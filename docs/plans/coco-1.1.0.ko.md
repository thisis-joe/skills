# COCO 1.1.0: 무엇을 어떤 순서로 바꿀 것인가

> **2026-10-26 진행 상태:** 사용자가 실제 스킬 수정을 요청했습니다. 아래의 구현 전 설명은 계획을 작성하던 당시의 기록입니다. 구체적인 수정 지점·변경 전후 예시·이유·검증은 새 문서 하나인 [1.0.0 → 1.1.0](../coco-1.0.0-to-1.1.0.md)에서 확인합니다. 현재 작업 상태의 기준은 영문 작업 계획입니다.

**실제 스킬 개선은 아직 시작하지 않았습니다.** 끝난 것은 두 대화의 결정과 실험 결과를 모아 명세·계획으로 정리한 일입니다. 이 요청은 문서 작성·검증·커밋까지 허용하며, 실제 구현, 새 모델·참가자 실험, 버전 변경, 설치, 푸시, PR, 머지, 배포를 승인하지 않습니다.

이 문서는 `60bfeca`의 [영문 작업 계획](coco-1.1.0.md)을 풀어 쓴 한국어 설명입니다. **실행 상태는 영문 계획 한 곳에서만 관리합니다.** 아래 상태는 그 기록을 설명한 것이며, 별도 상태표나 구현 승인이 아닙니다. 원본이 바뀌면 이 설명의 기준도 다시 확인합니다.

지켜야 할 동작은 [한국어 명세](../specs/coco-1.1.0.ko.md), 이 일을 하는 이유와 지금까지의 성과는 [배경 설명](../coco-1.1.0-rationale.ko.md)에서 볼 수 있습니다. 아래 예시는 앞으로 확인할 상황을 설명하기 위한 것이며, 새로 실행한 실험 결과가 아닙니다.

## 첫 작업과 그다음 작업

첫 작업은 **기존 사용법을 유지할 수 있는지 확인하는 것**입니다. 예를 들어 기존 `$coco-build` 요청을 바꾸지 않아도 사용할 수 있는지 봅니다. 그다음 합의한 네 단계 절차를 출시 기준 코드에 옮기고, 중요한 선택을 놓치는 문제를 고칩니다.

1. **F0 — 기존 사용법 확인:** 1.0.0과 실험 스킬의 차이를 조사하고, 유지할 사용법과 바뀌는 동작을 구분합니다.
2. **F1·F2 — 절차와 검사 준비:** 합의한 절차를 필요한 만큼 옮깁니다. 동시에 검사에 쓸 사용자 답변과 정답 기준이 서로 맞는지 확인합니다.
3. **F3·F4 — 문제 하나를 고치고 판단:** 미결정인 업무 규칙을 추측해서 구현하거나 변경 이유를 보고에서 빠뜨리는 문제를 좁게 고칩니다. 실제로 나아졌는지 확인해 유지·되돌림·재설계 중 하나를 결정합니다.
4. **필요할 때만 F5·U1·U2:** 같은 진행 상태를 여러 문서에 중복 관리한다면 줄이는 방안을 시험합니다. 실제 안내상의 불편이 있을 때만 사람 대상 안내 실험을 검토합니다.
5. **F6 — 전체 결과 검토:** 채택할 변경을 합친 상태에서 기존 동작과 명세를 다시 확인하고, 게시 전에 멈춥니다.

F0 다음에는 F1과 F2를 나눠 진행할 수 있습니다. F3에는 둘 다 필요합니다. F5는 F4의 판단이 기록된 뒤에 진행하고, U1은 F1의 대표적인 안내가 있으면 시작할 수 있어 F5를 기다리지 않습니다. 사람 참가자를 구하는 일은 정확성·권한 작업이나 사람에 대한 이점을 주장하지 않는 릴리스를 막지 않습니다.

## F0 — 기존 사용법이 계속 통하는지 확인

**할 일:** 출시 기준 코드와 실험 스킬을 비교합니다. 스킬 이름 29개뿐 아니라 직접 호출, 설치·메타데이터, 수동·자동 기본값, 전문 스킬 범위, 문서 작성 예외, Jira 규칙, 리뷰·커밋 시점까지 확인합니다.

**남길 결과:** 출시 기준의 구현 브랜치와 호환성 판단입니다. ‘호환성’은 앞의 `$coco-build` 예처럼, 기존 사용자가 요청이나 설치 방식을 바꿔야 하는지를 뜻합니다. 실험 브랜치 전체를 그대로 합치지 않습니다.

**끝났다고 볼 조건:** 실제 파일 차이와 사용법을 근거로 바뀌는 동작을 분류하고, 1.1.0으로 확정하기 전에 호환되지 않는 변경을 해결합니다. 과거 0.2.0 대상 비교는 이 1.0.0 호환성 검사를 대신하지 않습니다. 배포된 npm 패키지의 호환성을 주장하려면 레지스트리의 실제 배포본도 고정해 비교해야 합니다. 지금 있는 기록은 로컬 소스만 확인합니다.

**선행 조건·상태:** 이후 구현 요청이 필요합니다. **미시작**이며 F1 이후 작업은 F0을 건너뛰지 않습니다.

## F1 — 합의한 네 단계 절차를 출시 코드에 옮기기

**할 일:** 공통 workflow/contracts/routing과 관련 스킬·참조 문서에 필요한 안내·전환·완료 규칙만 옮깁니다. README도 실제 출시 후보와 맞춥니다.

**남길 결과:** 시작 안내부터 푸시 직전까지 같은 규칙을 따르는 스킬 묶음입니다. 처음에는 네 단계와 입문 스킬 열 개를 안내하고, 전체 29개 목록과 전문 스킬에도 접근할 수 있어야 합니다. 설명문의 오탈자를 고치는 것처럼 동작을 바꾸지 않고 범위가 분명한 단순 편집에는 불필요한 인터뷰나 문서 작성을 덧붙이지 않습니다.

**끝났다고 볼 조건:** 명세의 C1/C3/C4/C6/C8이 관련 문서에서 일치하고 실제 동작에서도 확인돼야 합니다. 명시적으로 고른 다음 스킬을 다시 승인받지 않고, 자동 흐름은 같은 명세에만 복원하며 푸시 직전에 멈춰야 합니다. 전문 스킬 동의는 정확한 사용자·프로젝트·스킬에만 적용하고 철회도 반영해야 합니다. 사용자 식별이나 개인 설정 저장소를 확인할 수 없으면 수동 선택으로 돌아가며, 공유·전역 기본값으로 바꾸지 않습니다.

Jira가 없는 프로젝트에서 적절한 설명형 브랜치를 그대로 쓸 수 있어야 합니다. 실험 build에 남은 "this format" 문구 때문에 Jira 형식을 다시 요구하지 않도록 common/build/push 규칙 전체를 확인합니다. 진행 중인 작업의 직접 리뷰 요청과 커밋·스테이징·미커밋·새 파일의 리뷰 범위도 보존합니다. 원본 출처·팀 재정의 기록을 함께 옮기되 원본 내용과 스냅샷 파일은 그대로 보존합니다.

**선행 조건·상태:** F0 이후. **미시작**.

## F2 — 검사가 사용자 답변을 제대로 판정하는지 확인

**할 일:** 임시 프로젝트에서 쓸 사용자 답변, 기대 결과, 실제 명령 실행 검사를 맞춥니다. ‘판정 기준’은 사용자가 정한 동작을 구현이 지켰는지 판단하는 정답입니다. 내부 코드 모양 대신 사용자가 쓰는 공개 인터페이스의 결과를 독립적으로 확인합니다.

예를 들어 이메일을 비교할 때 소문자로 맞춘다는 답만 받았다면, 출력도 소문자로 해야 하는지는 아직 모릅니다. 출력 표기를 답하지 않았는데 검사만 소문자를 강요하면 잘못된 검사입니다. 비교용 키와 출력 표기가 서로 중요한 선택이면 따로 다뤄야 합니다.

**남길 결과:** 사용자 답변이 빠지거나 구현이 잘못됐을 때 그 차이를 드러낼 수 있는 검증 도구와 기대 결과입니다. 실제 추가 질문이 생기면 정해 둔 질문 목록에 없더라도 사용자에게 전달돼야 합니다.

**끝났다고 볼 조건:** 이미 답한 선택은 복원하고, 답하지 않은 선택은 안전하게 보류하는지 확인할 수 있어야 합니다. 일부러 잘못된 동작은 검출되고 올바르게 되돌리면 통과해야 하며, 무관한 기존 동작은 보존돼야 합니다. 과거의 무효한 한 쌍과 고정한 실험 자료는 고쳐 쓰지 않고 남깁니다.

**선행 조건·상태:** F0 이후. 테스트·근거 파일의 담당을 나누면 F1과 병행할 수 있습니다. **미시작**.

## F3 — 중요한 선택을 놓치거나 변경 이유를 빼먹는 지점 고치기

**할 일:** build/clarify/공통 workflow 중 실제 결정을 내리는 지점에 최소한의 변경 하나를 적용합니다. 모든 작업에 긴 인터뷰를 추가하는 방식은 피합니다.

**남길 결과:** 필요한 질문이 구현 전에 실제로 나오고, 최종 보고에 최초 예상·실제 선택·달라진 이유가 남는 절차입니다.

**끝났다고 볼 조건:** C2/C7을 충족해야 합니다. 이미 정한 답은 재사용하고, 미결정인 중요한 업무 규칙만 채택 전에 질문합니다. 질문에는 구체적인 상황·대안·영향·추천과 그 이유를 포함합니다. 사용자에게 보이는 최종 보고는 수정된 명세와 맞는다는 말로 끝내지 않고 최초 예상과 실제 선택, 변경 이유를 비교해야 합니다. 해당 파일을 제공했다는 사실만으로 끝내지 않고, 필요한 규칙을 실제로 읽고 따랐는지 확인합니다.

**선행 조건·상태:** F1과 F2가 모두 필요합니다. **미시작**.

## F4 — 나아졌는지 확인하고 유지·되돌림·재설계 결정

**할 일:** 실행 전에 비교 사례, 소스, 사용자 답변·정답 기준, 평가표, 비용 공식, 예산을 고정합니다. 고치려는 문제가 나타날 수 있는 사례를 미리 정하고, 같은 조건에서 기존 방식과 F3 변경안을 실행해 비교합니다. 사용자 답변이나 검사의 정답 기준에 오류가 없는 사례여야 합니다.

**남길 결과:** 변경을 유지할지, 되돌릴지, 적용 조건부터 다시 설계할지에 대한 근거와 결정입니다.

**끝났다고 볼 조건:** 비교 우위를 주장하려면 최소 **5쌍**을 사용합니다. 실제 동작을 독립적으로 확인하고, 어느 규칙을 읽고 따랐는지에 대한 기록과 정체를 가린 대조 사례로 판정을 점검합니다. 품질 향상을 주장하려면 추정해서 구현한 정책을 나중에 고친 것으로 확인된 사례가 줄어야 합니다. 동시에 사용자 결정권 침해·절차 누락·약속한 동작 미충족·운영 실패가 늘면 안 됩니다.

불리한 결과도 보존하며 유리한 사례로 교체하지 않습니다. 미결정 사항 때문에 안전하게 멈춘 것은 완료와 구분하되, 거짓 보고나 기억 상실로 취급하지 않습니다. 검사가 잘못됐으면 결론을 보류하고, 기존 결과를 고쳐 성공으로 만들지 않습니다.

**선행 조건·상태:** F3 완료와 입력·기준 고정이 필요합니다. **미시작**.

## F5 — 같은 진행 상태를 여러 곳에 쓰는지 조사

**할 일:** spec/plan/context에서 수정 가능한 상태를 실제로 중복 관리하는지 봅니다. 예를 들어 같은 진행 목록을 계획 문서와 인수인계 문서에 각각 두어, 한쪽만 완료로 바뀔 수 있는 구조인지 확인합니다. 재사용하라는 문구만 더 강하게 쓰는 실험은 반복하지 않습니다.

**남길 결과:** K3에 대해 현재 상태를 유지할지, 중복 하나를 없애는 구조 변경을 시험할지 결정합니다. 중복이 없으면 그대로 두고 이 갈래를 종료합니다.

**끝났다고 볼 조건:** 변경한다면 명세·계획 두 문서, 최초 결정·대체 결정, 미결정 사항과 상태 관리 주체 한 곳을 보존합니다. 새 맥락에서의 인수인계 **5건**을 확인합니다. 이 항목의 단위는 인수인계 건수입니다. 별도로 비교 우위를 주장하려면 명세의 공통 규칙에 따라 같은 과제를 기존·변경 방식에 준 **최소 5쌍**도 비교해야 합니다. 효율 향상을 주장하려면 모든 절차·공개 인터페이스 동작 보존 조건을 충족하고, 변경안의 에이전트 실행 시간 중앙값이 기준안의 **80% 이하(비율 <=0.80)**여야 합니다.

**선행 조건·상태:** F4의 처리 결정이 기록된 뒤. **조건부·미시작**.

## U1 — 안내가 정말 불편한지 먼저 확인

**할 일:** workflow/start/discovery의 실제 안내에서 사람이 겪는 어려움과 변경할 여지를 확인합니다. 기존 예비 실험의 기준안은 이미 복귀 사용자에게 전체 지도를 반복하지 않았습니다. 변경 효과를 만들려고 기존 안내를 일부러 길게 만들면 안 됩니다.

**남길 결과:** R7의 안내 변경이 필요한지에 대한 판단입니다. 실제 불편이나 기존안·변경안의 차이가 없으면 문구를 고치지 않고 보류합니다.

**끝났다고 볼 조건:** 무엇이 불편하고 무엇만 달리 보여 줄 것인지가 실제 관찰로 구분돼야 합니다. 참가자를 구하지 못하면 사람에 관한 결과는 미확인으로 남깁니다. 모델이 답한 결과로 사람의 이해나 선택을 대신 판단하지 않습니다.

**선행 조건·상태:** F1의 대표적인 안내가 필요하지만 F5를 기다릴 필요는 없습니다. **조건부·미시작**.

## U2 — 필요성이 확인된 안내만 실제 사람에게 시험

**할 일:** U1에서 타당하다고 본 안내 변경을 COCO에 익숙하지 않은 실제 참가자 최소 **5명**에게 시험합니다. 참가자의 동의를 받고, 무엇을 좋아졌다고 볼지 우선 측정할 항목과 통과 기준을 먼저 고정합니다.

**남길 결과:** 실제 사람이 다음 행동을 고르고 그 목적을 설명한 관찰 결과입니다. 선택·설명·전문 스킬 찾기·승인 이해·능동적인 선택 시간·재설명 요청을 따로 기록합니다.

**끝났다고 볼 조건:** 모두에게 같은 첫 안내를 주고, 동등한 후속 과제와 표시 순서를 균형 있게 배정합니다. 바꾸는 것은 전체 지도를 반복 표시하는지뿐입니다. 추천·이유·예상 결과·복사할 요청문, 전체·전문 스킬 접근과 사용자 권한은 유지합니다. 실제 관찰 없이 학습이 쉬워졌다거나 사람의 노력이 줄었다고 주장하지 않습니다.

**선행 조건·상태:** U1의 필요성 확인, 동의한 참가자 확보, 우선 측정할 항목·통과 기준 고정이 필요합니다. **조건부·미시작**. 참가자 확보는 다른 정확성·권한 작업의 선행 조건이 아닙니다.

## F6 — 채택할 변경을 합친 상태로 마지막 검토

**할 일:** 실제 통합 변경과 명세 C1–C8 전체를 독립적으로 검토합니다. 저장소 필수 검사와 영향을 받는 공개 동작·실제 실행·설치 검사를 임시 대상에서 수행합니다.

**남길 결과:** 원본 출처, 검증 근거, 작업별 커밋과 되돌림 기록을 갖춘 릴리스 후보입니다. 일부 작업의 통과를 전체 출시 준비 완료로 취급하지 않습니다.

**끝났다고 볼 조건:** F0의 호환성·버전 판단을 확정하고 실제 통합 결과가 명세를 지켜야 합니다. 소스·검사 설계·결과 주장을 독립 검토합니다. 검토가 끝나도 자동으로 게시하지 않고 그 전에 멈춥니다.

**선행 조건·상태:** F1·F4와 F5·U1의 처리 결정이 필요합니다. 사람에 대한 이점을 주장하는 데 필요할 때만 U2가 선행 조건이 됩니다. **미시작**.

## 모든 단계에서 지킬 판단 기준

실제 사용자 결정권 침해, 권한 확대, 결정 출처 손실, 공개 동작 실패나 필수 절차 누락이 생기면 해당 변경은 채택하지 않습니다. 지켜야 할 의무는 남기고 변경만 되돌리거나 적용 조건을 다시 설계합니다. 새로 생긴 중요한 결정은 사용자가 내립니다.

다음 구분을 유지합니다.

- **맞는 결과와 동의는 다릅니다.** 사용자에게 묻지 않은 기본값이 우연히 정답과 같아도 합의로 보지 않습니다. 나중에 그 값을 확인받았지만 동작이 바뀌지 않았다면, 그 확인을 ‘잘못된 정책을 고친 횟수’로 세지도 않습니다.
- **인수인계는 실제로 이어서 할 수 있어야 합니다.** 새 작업자가 남은 자료에서 현재 결정·미결정 사항·근거·다음 행동을 복원하고, 허용된 일을 끝내며 무관한 데이터를 보존해야 합니다. 새 대화에 기술 실행 권한을 다시 줬다는 사실만으로 동의가 대화 사이에 자동 유지된다고 주장하지 않습니다.
- **문서와 검사 이름만으로 증거가 생기지 않습니다.** 바뀐 명세나 자체 리뷰는 최종 보고에 빠진 최초 가정이나 누락된 실행 근거를 대신하지 못합니다. 구현·리뷰·실제 실행 검증 상태를 따로 보고합니다.
- **실행 시간은 사람의 수고가 아닙니다.** 전체 시도와 양쪽이 모두 완료한 사례의 비용을 따로 기록하고, 시간과 토큰도 구분합니다. 에이전트 실행 시간으로 금액이나 개별 규칙의 인과적 비용을 단정하지 않습니다.
- **새 실험에는 새로 결정할 이유가 있어야 합니다.** 효과가 없으면 잘 작동하는 기존 동작을 유지합니다. 효율 기준 미달은 그 주장의 기각입니다. 다시 시험하려면 결과에 영향을 주는 가설 변경이나 검사 수정 이유를 사전에 남깁니다. 유리한 결과가 나올 때까지 반복하지 않습니다.

변경은 작업 단위로 커밋해 근거를 삭제하지 않고도 되돌릴 수 있어야 합니다. 상태는 실제 커밋과 대조합니다. 공통 규칙은 통합 담당자 한 명이 수정하고, 독립 조사는 병행하더라도 같은 파일을 동시에 수정하지 않습니다. 수정은 build, 문제 지적은 review, 실행 근거는 verify가 맡습니다.

파괴적 초기화, 광범위한 재작성, 임의의 추적 도구 추가, 첫 안내 삭제, 동의·데이터 검사 축소는 하지 않습니다. 읽었지만 따르지 않은 규칙과 노출이 확인되지 않은 규칙도 구분합니다. R1/R3 제거는 보류하고, R4의 근거 재사용과 R6의 독립·다양한 모델 리뷰 또는 실제 테스트 민감도 검사는 별도 가설로 둡니다. 사후 판정자를 개발 과정의 개입으로 세거나 원저자의 명성을 입증하려고 실험을 만들지 않습니다.

## 아직 정하지 않아도 되는 것

최종 호환성·버전 판단은 F0의 구체적인 변경 전후 조사 뒤에 합니다. 구조적으로 줄일 대상은 F5에서 실제 중복을 찾은 뒤에 정합니다. 사람 대상 실험의 주 지표와 수치 기준은 U1에서 확인한 문제와 구체적인 실험 계획을 바탕으로 정합니다. 이 때문에 이미 합의한 38개 결정을 다시 묻거나 계획 작성 완료를 미루지 않습니다. 이후 구현 요청이 주어지면 이미 승인된 범위의 일상적인 단계는 그 동의를 재사용합니다.

과거 보고서의 이름과 연결하면, **R5는 질문 개선**으로 F2~F4에서 다루고,
**R2는 기록 재사용·중복 축소**로 F5에서 다룹니다. **R7은 반복 안내 개선**으로
U1·U2와 연결됩니다. 과거 실험은 끝났으며, 이 대응표가 그 실험을 다시 실행하라는 뜻은 아닙니다.

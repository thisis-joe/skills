# COCO 1.1.0에서 사용자가 기대할 수 있어야 하는 동작

> **2026-10-26 진행 상태:** 사용자가 실제 스킬 수정을 요청했습니다. 아래의 구현 전 설명은 계획을 작성하던 당시의 기록입니다. 구체적인 수정 지점·변경 전후 예시·이유·검증은 새 문서 하나인 [1.0.0 → 1.1.0](../coco-1.0.0-to-1.1.0.md)에서 확인합니다. 현재 작업 상태의 기준은 영문 작업 계획입니다.

목표는 에이전트가 **합의한 내용대로 일하고, 모르는 중요한 선택은 사용자에게 묻고,
다른 대화의 에이전트도 남겨 둔 파일을 읽어 작업을 이어가게 하는 것**이다.
이 문서는 그 목표를 위해 지켜야 할 요구사항을 설명한다. 아래 동작이 모두 구현됐다는 보고는 아니다.

> `60bfeca`의 [영문 명세](coco-1.1.0.md)를 바탕으로 쉽게 풀어 쓴 한국어 설명이다.
> 기존에 승인된 내용과 권한은 그대로이며, 이 설명을 작성했다고 새로운 스킬 구현이나
> 실행 권한이 생기지는 않는다. 실행 상태의 유일한 관리 기준은
> [영문 계획서](../plans/coco-1.1.0.md)다.

사용자가 이미 정한 [38개 결정](staged-development.md)을 유지한다.
`1.1.0`은 호환성을 검토한 뒤 확정할 목표 버전이다. 원래 계획 요청이 허용한 일은
명세·계획·문서를 작성하고 그 문서를 커밋하는 것까지다. 스킬 변경, 추가 모델 실행 실험,
설치, 패키지 버전 변경, 게시는 허용하지 않았다.

아래 **가상 예시**는 앞으로 어떤 동작을 기대하는지 설명하기 위한 것이다.
실제 실험에서 관찰한 결과는 뒤의 “기존 실험에서 유지해야 할 결론”에 따로 적었다.

## C1. 지금 필요한 스킬을 알려 주고, 다른 스킬도 찾아 쓸 수 있게 한다

처음에는 네 단계와 입문 스킬 10개를 소개한다.

- 요구사항 정리: `coco-clarify`, `coco-spec`, `coco-plan`
- 구현: `coco-build`, `coco-debug`
- 리뷰와 검증: `coco-review`, `coco-verify`
- 릴리스: `coco-push`, `coco-merge`, `coco-ship`

이것은 사용자가 10개를 모두 차례로 실행해야 한다는 뜻이 아니다. 지금 필요한 다음 스킬과
그 이유를 알려 주되, 전체 29개 스킬을 설치 대상으로 유지하고 계속 사용할 수 있게 둔다. 전체 목록 요청,
전문 스킬 탐색, 숙련자가 이름을 지정해 직접 호출하는 방법도 유지한다.
메뉴를 짧게 보이게 하려고 기존 스킬을 없애거나 필요한 전문 스킬을 숨기지 않는다.

**가상 예시:** “CSV 가져오기 기능을 만들고 싶다”는 요청에서 동작이 아직 정해지지 않았다면
`coco-clarify`를 추천한다. 이미 충분한 명세와 계획이 있다면 그 문서를 재사용해
`coco-build`로 갈 수 있다. 같은 안내에서 “전체 스킬을 보고 싶다”는 요청도 할 수 있다.

**확인 조건:** 처음 사용하는 사람을 위한 안내에 다음 단계가 분명히 드러나고,
전체 목록과 직접 호출 경로도 남아 있어야 한다.

## C2. 이미 정한 것은 찾아 쓰고, 아직 모르는 중요한 선택만 묻는다

**이미 정한 선택**은 명세나 승인된 기록에 답이 있는 것이다. 에이전트가 그 기록을 읽고
복구해야 하며, 사용자에게 같은 결정을 다시 시키지 않는다. 저장소에서 확인할 수 있는
사실도 먼저 직접 조사한다.

**아직 모르는 선택**은 사용자에게 필요한 결과를 바꾸지만 답이 정해지지 않은 것이다.
이때는 실제 상황, 선택 가능한 대안, 각 대안의 영향, 추천과 그 이유를 함께 묻는다.
답이 없으면 그 부분을 안전하게 미결정 상태로 남긴다. “기술 작업은 자동으로 진행해”라는
허용을, 보여 주지도 않은 업무 규칙까지 대신 정해도 된다는 뜻으로 쓰지 않는다.
사용자가 제시된 추천을 선택하거나 그 기본값대로 맡기겠다고 하면 그 선택을 따른다.
그 위임을 아직 보여 주지 않은 중요한 선택까지 넓히지는 않는다.

**가상 예시:** 상품 코드 ` A1 `과 `a1`을 같은 상품으로 볼지가 미정이라고 하자.
“같게 보면 같은 상품을 가리키는 두 행으로 판단하고, 다르게 보면 서로 다른 상품으로
판단합니다. 표기 차이 때문에 같은 상품을 다른 상품으로 구분하지 않으려면 같게 보는 안을
추천합니다”라고 설명하고 묻는다. 같은 상품의 중복 행을 합칠지, 건너뛸지, 오류로 거절할지는
별도의 규칙이다. 이미 정했다면 그 결정을 찾아 따르고, 중요한 선택인데 아직 정하지 않았다면
따로 묻는다. 반대로 명세에 이미 “대소문자를 구분한다”고 적혀 있다면 그 선택을 복구해 따른다.

**확인 조건:** 알고 있던 선택을 다시 묻지 않아야 한다. 모르는 중요한 선택은 몰래
기본값으로 정하지 않고 질문하거나 미결정으로 남겨야 한다.

## C3. 다음 스킬 실행은 선택을 받고, 자동 진행은 한 명세 안에서만 한다

아직 선택하지 않은 스킬로 넘어갈 때는 무엇을 왜 실행하려는지, 어떤 결과가 나올지를
먼저 알리는 것이 기본이다. 같은 질문에서 “다음 스킬만 한 번 실행”과
“이 명세 범위의 기본 단계를 자동으로 진행” 중 선택할 수 있게 한다.
이미 명시적으로 요청한 행동의 승인을 다시 묻지는 않는다.

여기서 **기본 단계 자동 진행**은 한 명세와 합의된 범위 안에서 필요한 기본 스킬을 이어
실행하는 것이다. 단계가 바뀌면 알리고, 구현·리뷰·검증·수정·커밋을 마친 뒤 **push 전에 멈춘다**.
이 권한을 다른 명세나 게시·병합·배포로 옮기지 않는다. 같은 명세를 이어받을 때도
기록된 선택과 범위를 확인해 유지한다. 보조 문서를 읽거나 선택된 스킬의 검사를 하는 것은
새 스킬 전환이 아니다.

**가상 예시:** 사용자가 “`coco-review`로 검토해 줘”라고 했다면 이미 리뷰 실행을 선택한 것이다.
“리뷰를 해도 될까요?”라고 다시 묻지 않는다. 반면 단순히 “다음에는 리뷰가 필요합니다”라고
추천한 것만으로 리뷰를 실행하지는 않는다.

**확인 조건:** 선택하지 않은 전환을 몰래 실행하지 않아야 한다. 이미 받은 선택을
중복 확인하지 않아야 하며, 자동 진행이 다른 명세나 push 이후 작업으로 번지지 않아야 한다.

## C4. 전문 스킬을 추가할 때는 별도로 설명하고 선택을 받는다

보안·성능 같은 전문 스킬을 추가하려면 무엇을 확인하고 왜 필요한지, 예상 확인 범위와
비용을 설명한다. 기본 단계 자동 진행을 골랐어도 모든 전문 스킬을 허용한 것은 아니다.
기존의 명시적 동의는 **해당 사용자·프로젝트·스킬**에만 적용하고, 철회도 그 범위대로 반영한다.

개인 선택을 팀 전체의 공유 규칙이나 전역 설정으로 저장하지 않는다. 사용자나 프로젝트를
확인할 수 없거나 개인 설정을 안전하게 저장할 수 없다면 자동 허용으로 간주하지 않는다.
전문 스킬을 거절해도 필요한 동작과 일반적인 필수 검사는 남는다.
추가 검토를 하지 않아 확인하지 못한 범위나 독립 리뷰의 부재는 보고한다.

**가상 예시:** 한 사용자가 이 프로젝트에서 `coco-security` 자동 사용을 허용해도,
다른 프로젝트나 다른 사용자의 작업, `coco-performance` 실행까지 허용한 것은 아니다.
해당 보안 스킬의 자동 사용을 취소하면 그 허용을 해제한다.

**확인 조건:** 어떤 사용자·프로젝트·스킬에 받은 동의인지 구분할 수 있어야 한다.
거절이나 철회를 이유로 필수 검사를 없애서는 안 된다.

## C5. 새 에이전트가 파일을 읽고 이어서 일할 수 있게 남긴다

동작을 추가하거나 바꾸기 전에는 프로젝트 관례에 맞는 명세와 계획을 저장하거나 재사용한다.
명세에는 무엇을 만들고 어떻게 맞는지 확인할지를 적고, 계획에는 할 일과 순서·검사를 적는다.
기존 문서가 충분하면 새 문서를 만들지 않는다. 설명만 하는 요청이나 명확한 정적 수정에는
이 문서 쌍을 요구하지 않는다.

**인계**는 새 에이전트나 다른 대화가 남아 있는 파일·커밋 기록을 읽고 작업을 이어가는 것이다.
이미 정한 선택뿐 아니라 아직 정하지 않은 선택, 완료한 일, 남은 일, 확인 근거,
다음 행동과 허용 범위를 찾을 수 있어야 한다. 완료/대기 상태는 지정된 한 곳에서만 관리한다.

**가상 예시:** 첫 에이전트가 CSV 가져오기까지만 만들고 집계 기능을 남겼다면,
새 에이전트는 파일에서 “가져오기는 완료, 집계는 미완료, 0원 상품의 집계 방식은 아직 미정”을
확인할 수 있어야 한다. 미정인 것을 지워서 전부 끝난 것처럼 만들면 안 된다.

**확인 조건:** 새 에이전트가 실제로 남은 자료를 읽고 현재 선택과 미결정 사항,
완료/대기 작업, 근거, 다음 행동과 범위를 복구할 수 있어야 한다.

## C6. 실행해서 확인하고, 구현 완료와 개발 완료를 구분한다

프로젝트의 `AGENTS.md`·`CLAUDE.md`와 필수 검사 규칙을 따른다.
동작을 바꿀 때는 그 동작을 확인하는 검사가 먼저 실패하고(RED), 구현 뒤 통과하는지(GREEN)
관찰한다. 적절한 자동 검사 방법이 없으면 실행 가능한 재현 절차와 그 이유를 남기고,
자동 검사로 확인한 것처럼 말하지 않는다. 실제 사용자가 쓰는 경로에서 동작을 확인한다.
UI·API·CLI는 그 기능에 맞춰 선택할 수 있는 확인 경로의 예다.

구현자는 필요한 검사를 하고 자체 점검, 즉 자신이 만든 코드를 확인한 뒤 작업 단위 커밋을 남긴다.
이때는 **구현 완료·리뷰 대기**다. 공식 리뷰는 별도로 하고, 가능하면 새로운 맥락의 검토자가
맡는다. 리뷰 담당자는 발견한 문제를 돌려주고, 코드를 고치는 일은 구현자가 맡는다.
독립 리뷰를 못 했다면 그 한계를 알리고, 사용자가 그 한계를 받아들일지 결정하게 한다.
리뷰에서 받아들인 수정은 구현자가 후속 커밋으로 반영하고, 영향을 받은 부분을 다시 확인한다.

필요한 리뷰 지적을 해결하고 실제 실행 검증과 커밋까지 마쳐야 개발 완료라고 할 수 있다.
독립 리뷰 부족을 사용자가 받아들였더라도, 필수 실행 검증까지 생략할 수는 없다.

**가상 예시:** 버튼의 단위 테스트는 통과했지만 필수 브라우저 동작을 실행하지 못했다면
“검증 대기(verification-pending)”다. 테스트가 통과했다는 이유로 개발 완료라고 보고하지 않는다.

**확인 조건:** 실제 동작을 확인한 기록, 자체 점검과 독립 리뷰의 구분, 작업 단위 커밋을
찾을 수 있어야 한다. 필요한 실행 근거가 없으면 검증 대기 상태를 유지해야 한다.

## C7. 최종 보고에 원래 기대와 실제 결과를 직접 비교해 쓴다

최종 보고 자체에 원래 기대한 설계, 실제 선택, 달라진 이유와 영향, 근거와 현재 단계를 적는다.
명세를 새 결론으로 고쳤다고 원래 가정을 지우지 않는다. “자세한 내용은 문서 링크 참고”만으로
이 비교를 대신하지 않는다. 중요한 차이가 없다면 차이가 없다고 쓴다.

**가상 예시:** 처음에는 0원 상품을 집계에서 제외하기로 했지만 사용자가 포함하도록 바꿨다면,
최종 보고에 “원래는 제외, 실제는 사용자 변경 요청대로 개수에 포함, 이유는 새 회계 기준,
영향은 집계 개수가 달라지는 것”이라고 설명한다. 확인 근거와 현재 진행 단계도 함께 적는다.
이 예시는 실제 실행 결과가 아니다.

**확인 조건:** 최종 사용자 보고만 읽어도 원래 기대와 실제 선택, 차이의 이유·영향을 알 수
있어야 한다. 바뀐 명세만 남기거나 새 기준과만 비교해서 원래 가정을 숨겨서는 안 된다.

## C8. 규칙을 어디서 가져왔고 왜 바꿨는지 찾을 수 있게 한다

규칙을 합치거나 바꾸면 어느 원본 기법을 가져왔는지, 원래 어떤 방식으로 효과를 내려 했는지,
현재 어느 파일에서 관리하는지, 무엇을 왜 바꿨는지를 남긴다. 출처 표기와 핵심 규칙에 관한
결정, 팀에 맞춰 조정한 이유를 보존한다.

**가상 예시:** 원본의 리뷰 시점을 팀에서 다르게 정한다면, 원본의 방식과 팀이 선택한 방식,
그 이유를 구분해 적는다. 팀이 고른 방식을 원작자도 그렇게 정했다고 설명하지 않는다.

**확인 조건:** 바뀐 통합 규칙의 담당 위치, 영향을 받은 원본 기법과 변경 이유를 찾을 수
있어야 한다. `sources/`에 보관한 원본은 출처 확인 자료이지, 에이전트가 실행할 지침이 아니다.

승인된 38개 결정과 충돌하는 내용은 구현자가 몰래 타협하지 않는다.
충돌하는 구체적인 동작을 설명하고 사용자의 결정을 받아야 한다.
코딩 속도, 질문 수, 문서 수, 기반 모델과의 승패만으로 이 절차의 가치를 판단하지 않는다.

## 참고 1. 앞으로 바꿀 부분과 선후 관계: K0~K4

다음 표는 위 요구사항을 구현할 때의 작업 구분이다. 지금 구현했다는 뜻은 아니다.

| ID | 바꿀 부분 | 먼저 필요한 것 |
| --- | --- | --- |
| K0 | 로컬 1.0.0 기준과 실험용 절차의 차이를 정리한다. 기존 사용 방식을 유지하고 의도한 변경을 밝힌다 | 없음 |
| K1 | 릴리스 기반 후보에서 단계 안내, 스킬 전환, 전문 스킬 선택, 완료 판단이 서로 충돌하지 않게 맞춘다 | K0 |
| K2 | 중요한 선택을 코드에 반영하기 전에 필요한 질문 절차를 실제로 거치게 하고, 최종 보고에 원래 기대/실제 결과/이유를 남긴다 | K1, 아래 참고 3의 믿을 수 있는 확인 방법 |

다시 고칠지 정한 다음에 K3의 효율 개선을 검토한다. K4는 별도로 판단하며 그대로 둘 수도 있다.
보류된 R1/R3 제거안이나 R4/R6 시험을 이 릴리스에 함께 넣지 않는다.

예를 들어 같은 완료/대기 목록을 두 곳에서 따로 수정해 서로 달라질 수 있는 상황이다.
그런 실제 기록이 없다면 더 줄일 것이 있다고 가정하지 않는다. 명세와 계획은 계속 필요하다.

## 참고 2. 기존 실험에서 유지해야 할 결론: R5·R2·R7

기존 실험의 입력, 결과를 센 전체 사례 수와 제외 사례, 오류와 판정은 그대로 남긴다.
서로 다른 질문을 다룬 [워크플로 v2](../evaluation/staged-development/report-v2.md),
[협업 비교](../evaluation/collaboration-value/report.md),
[분리된 파일럿](../evaluation/procedure-refinement/report.md)을 합쳐 하나의 성공률로 만들지 않는다.
이 자료는 전체 사용자 집단의 성공률, 원본 소스 트리와의 직접 비교, 실제 사람의 학습이나
노력을 측정한 결과를 제공하지 않는다. 명확한 작업을 다룬 최초 연구와 이후 보고 수정도
별도의 과거 관찰로 남긴다.

### R5. 질문을 더 잘하게 만들겠다는 문구는 아직 입증된 해결책이 아니다

연락처 통합 실험의 불완전한 비교쌍을 원래 기록 그대로 보존한다.
그 비교의 정책 수정 횟수는 0회로 바꾸지 않고, 판단할 수 없다는 뜻의 `null`로 남긴다.
시험했던 결정 항목 안내 문구를 입증된 해결책으로 채택하지 않는다.

다음에 시험하려면 먼저 “누가 어떤 선택에 답하는가”와 “어떤 출력이 정답인가”가 맞아야 한다.
정답 판정에 필요한 업무 규칙은 모두 답할 수 있어야 하고, 실제로 나온 추가 질문도
결정권자에게 전달돼야 한다. 이미 답이 있는 선택을 찾아 쓰는 경우와,
모르는 선택을 사실대로 미정으로 남기는 경우를 모두 확인한다.

검사가 처음 실패하는 것은 새 기능을 만들 때 예상된 RED일 수 있다.
답을 기다리며 막아 둔 기능을 답변 후 완성한 것도, 잘못 정한 업무 규칙을 고친 횟수로 세지 않는다.

### R2. 기존 기록 재사용은 두 조건 모두 됐고, 더 빠르다는 기준은 못 넘었다

파일럿의 두 조건은 모두 5개 사례에서 작업 내용을 복구하고 이어서 일을 끝냈다.
재사용을 더 강하게 강조한 문구는 20% 시간 감소 기준을 넘지 못했다.
문구를 바꾼 시험이지, 중복된 진행 정보의 구조를 없애 본 시험은 아니었다.

새로 구조를 줄이겠다면 실제 중복 기록부터 찾아야 한다. 두 저장 문서, 원래 결정과
변경된 결정의 근거, 아직 모르는 선택을 보존한다. 합의가 분명한지, 내용이 일관되는지,
근거 출처를 찾을 수 있는지, 새 에이전트가 이어서 일할 수 있는지, 최종 보고가 맞는지와
실제 동작을 모두 확인한다.

효율 개선을 주장하는 기준은 그대로다.
**제안 방식의 에이전트 실행시간 중앙값 ÷ 기존 방식의 중앙값 <= 0.80**이어야 한다.
즉, 중앙값 기준으로 최소 20% 줄어야 한다. 이 속도 기준을 만족해야만 공유 절차가
가치 있다는 뜻은 아니다.

### R7. 이미 짧게 안내하던 기준을 일부러 장황하게 만들지 않는다

파일럿의 기존 절차는 이미 반복 개요를 생략했고 제안 방식의 답변이 더 길었다.
이 결과를 그대로 둔다. 비교에서 유리해지려고 기존 방식을 일부러 장황하게 만들지 않는다.

사람을 대상으로 시험하려면 실제로 사용자가 겪은 불편과 실제로 달라지는 안내가 있어야 한다.
둘 중 하나라도 없다면 변경 시험을 보류한다. 통합 축소 계획에 적힌 참가자 연구는 아직
실행하지 않았다. 모델의 답변을 평가한 결과는 실제 참가자의 연속된 사용 경험을 대신하지
못하며, 사람이 더 쉽게 배웠거나 선택했다고 입증하지도 못한다.

## 참고 3. 다음 비교에서 무엇을 확인해야 하는가

**규칙을 읽었다는 것**은 해당 파일을 읽은 기록이 있다는 뜻이다.
**실제로 따랐다는 것**은 행동까지 맞았다는 뜻이다. 예를 들어 모르는 상품 구분 기준을
정하기 전에 사용자에게 물어야 한다면, 파일을 읽은 흔적만으로는 부족하다.
실제 질문과 답변, 그 뒤의 코드 선택을 따로 확인해야 한다.

다음에 비교 주장을 하려면 관련 절차마다 미리 정해 고정한 대응 사례쌍을 최소 5개 사용한다.
대응 사례쌍은 같은 과제를 기존 방식과 제안 방식에 주어 비교하는 것이다.
도구 역량, 권한, 예산을 같게 맞추고, 과제에 맞는 실제 사용 경로의 결과를 독립적으로 확인한다.
어느 조건인지 이름을 가린 상태에서 평가하고, 일부러 틀린 결과나 잘못된 완료 보고를
넣은 확인용 사례의 문제도 근거를 들어 잡아내는지 살핀다.

실행 전에 과제 입력과 평가할 결과, 질문과 결정권자가 답할 내용, 통과 기준, 중단 조건을 고정한다.
모든 시도를 남긴다. 확인 방법에 문제가 있으면 결론을 낼 수 없는 결과로 남기며,
그대로 승패를 정하지 않는다. 후속 비교를 하려면 측정 방식이나 입력에서 무엇을 바꿨고
왜 바꿨는지 먼저 기록한다. 유리한 사례가 나올 때까지 표본을 골라서는 안 된다.
내용과 조건이 바뀌지 않은 유효한 근거는 다시 쓸 수 있다.

## 참고 4. 1.1.0이라는 버전과 기존 사용자에 대한 확인

`1.1.0`은 아직 호환성을 보증하는 번호가 아니다. 기존에 되던 요청이 계속 되는지
릴리스 후보에서 확인한 다음 버전을 판단해야 한다. 스킬 이름이 같다는 사실만으로는 부족하다.

1. 스킬 호출 이름, 설치 범위, 기존 파일의 소유권을 지키는 설치 보호, 전체 스킬 탐색,
   사용자가 이미 명시한 권한을 보존한다.
2. 다음 스킬로 넘어갈 때 묻는 방식, 명세·계획을 저장해야 하는 조건, 리뷰와 커밋의 순서,
   Jira 적용 조건처럼 사용자가 실제로 겪는 기본 동작의 변화를 확인한다.
   Jira를 쓰지 않는 프로젝트에서 이미 적절한 설명형 브랜치를 쓰고 있다면 유지한다.
   후보 build 문구의 "this format"과 다르면 확인하라는 표현 때문에 무관한 Jira 확인이
   다시 필요해져서는 안 된다. 프로젝트가 Jira 규칙을 실제로 요구하면 정확한 Jira Summary와
   Git 이름 검증을 유지한다.
3. 기존 1.0.0에서 지원하던 대표 요청을 새 후보에서 실제로 실행한다.
   `622975e`와 0.2.0을 비교한 결과는 1.0.0 호환성 확인을 대신하지 않는다.
   npm에 공개된 패키지 사용자에 관해 주장하려면 실제 레지스트리 배포물을 고정해 비교한다.
   로컬 태그의 파일이 같다는 사실만으로 그 배포물까지 확인한 것은 아니다.
4. 승인된 동작을 지키기 위해 기존 사용법을 깨야 한다면, 무엇이 어떻게 달라지고
   사용자가 바꾸는 데 어떤 비용이 드는지 보여 준다. 호환되는 방식을 유지할지,
   메이저 릴리스를 목표로 할지 결정한다. 1.1.0에 맞추려고 승인된 결정을 몰래 완화하지 않는다.
   이것은 나중에 릴리스할 때의 조건이며 이 계획 설명을 쓰지 못할 이유는 아니다.

패키지 메타데이터 변경, 릴리스 전 패키징, 게시는 나중에 별도로 허용된 릴리스 작업에서 다룬다.

## 참고 5. 어떤 소스와 기록을 기준으로 삼는가

영문 명세의 계획 기준일은 2026-10-25다.

- 로컬 1.0.0 태그가 실제로 가리키는 커밋은 `84a59a2`이며, 그 커밋의 파일 전체는
  `88d1c84`와 같다. 이는 로컬 Git 기록의 확인이지 레지스트리 패키지 내용을 새로 확인한 결과가 아니다.
- 실험용 스킬 스냅샷은 `622975e`이며 `a19c5fb`에서도 그 스킬 내용은 바뀌지 않았다.
  로컬 1.0.0 태그에는 실험용 공유 4단계 워크플로가 없다. 실험용 구현이나 모델 실험을
  검증된 1.0.0 공개 배포 기능 또는 최종 1.1.0 패키지 시험이라고 설명하지 않는다.
- 원래 계획 브랜치는 근거를 보존하려고 `a19c5fb`에서 시작했다.
  향후 실제 구현은 릴리스 기반 통합 브랜치에서 검토한 변경만 골라 옮겨야 한다.
  실험 브랜치의 패키지 버전 표기가 1.0.0이어도 실제 스킬 내용까지 릴리스와 같다는 증거는 아니다.

자세한 파일 식별 정보는 [기준 상태 확인 기록](../evaluation/coco-1.1.0/baseline.json)에 있다.
향후 옮길 변경에는 출처 설명 정보도 포함한다. `coverage.json`의 131개 항목 중 64개에
워크플로 참조와 팀이 다르게 정한 이유를 가리키는 링크를 추가한다.
원래 핵심 규칙, 조정 사실, 보관된 업스트림 원본 파일은 바이트를 그대로 보존한다.
이번 계획 요청은 이 정보도 바꾸지 않는다.

## 이 문서를 다 썼다는 것과 기능을 만들었다는 것은 다르다

이 계획 요청의 완료는 두 대화에서 정한 내용, 소스 이력, 릴리스와 실험의 차이,
이미 확인한 것과 아직 모르는 것, 앞으로의 확인 조건과 작업 순서를 문서로 남기고
독립적으로 검토·확인하는 것이다. 문서와 근거 자료를 통합할 뿐,
`skills/`, `sources/`, 런타임 스크립트·테스트, 설치 프로그램, 버전 메타데이터는
`a19c5fb`와 바이트 단위로 같아야 한다.

**이 요청으로 향후 구현을 시작하거나 허용한 것이 아니다.** 실제 참가자 확보,
사람 대상 주요 평가지표와 통과 기준, 최종 호환성 선택은 그 작업을 할 때 필요한 조건이다.
이 조건이 아직 갖춰지지 않았다고 결과를 꾸며 내거나, 관련 없는 계획 정리와
올바른 동작을 확인하는 일을 막아서는 안 된다.

작업 순서는 [한국어 계획 설명](../plans/coco-1.1.0.ko.md), 목적과 지금까지의 결과는
[한국어 배경 설명](../coco-1.1.0-rationale.ko.md)에서 읽을 수 있다.
실제 실행 상태는 계속 [영문 계획서](../plans/coco-1.1.0.md) 한 곳에서만 관리한다.

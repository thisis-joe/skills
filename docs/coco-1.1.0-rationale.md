# Why COCO 1.1.0 is worth a bounded next step

> Update 2026-10-26: implementation is now authorized. Planning-only statements below describe the earlier closure. The single concrete change map is [1.0.0 → 1.1.0](coco-1.0.0-to-1.1.0.md); the English plan owns current execution state.

COCO has produced a source-accounted procedure package and a team-owned development
contract, with observed successful handoffs and usable next-step advice. The next
investment has a concrete purpose: connect that experimental contract to the
release and repair demonstrated decision/adherence gaps. Evidence does not yet
establish lower human effort, easier learning, economic payoff or general superiority.

This explanation is for maintainers deciding whether and how to continue. The
[specification](specs/coco-1.1.0.md) owns future behavior; the
[plan](plans/coco-1.1.0.md) alone owns execution status. No skill improvement is
implemented by this planning document.

## From three authors to a team procedure

The original aim was to combine useful techniques while making them easier to
choose and compose. The [source inventory](source-index.md) accounts for 131
upstream items: Matt 38, Addy 34 and pstack 59. They have explicit destinations
and adaptation decisions: 67 adapted, 49 merged and 15 reference modes. The package
provides 29 purpose-based entrypoints, shared rules, conditional specialists,
installation protection and validation. These are identifiable engineering outputs,
not just an aspiration that combining good advice must improve it.

The original philosophies are not identical. Matt emphasizes developer control,
small composable tools and dependency-aware questions; Addy emphasizes disciplined
engineering loops and evidence; pstack emphasizes design depth and trustworthy
delegation/verification. COCO records compromises between them. For example,
focused interviewing differs from full-frontier grilling; saved spec/plan documents
are a team choice; independent or diverse-model review became conditional.
The [upstream audit](evaluation/collaboration-value/upstream-intent.md) retains
these distinctions. Coverage does not prove that every original causal mechanism
was preserved, and the original trees were not direct experimental arms.

The user's 38 decisions made the combined philosophy explicit: **people own goals
and consequential business choices; the agent performs agreed changes and reports
observable evidence**. Four stages organize the work. Initial orientation presents
ten introductory skills while the full specialist catalog stays accessible.
These decisions are the team's contract, with authorship and tradeoffs traceable.

The old 0.2.0 worker's safe all-zero-output question was not memory loss. Likewise,
a compatible unasked business default is not user agreement. These distinctions
are useful results: they keep future optimization from rewarding silence or false
completion. The experimenter-created owner/oracle mismatch also remains a visible
measurement limitation rather than an alleged product defect.

## Before, experimental state and intended 1.1.0

The local tagged 1.0.0 release baseline is `84a59a2`, tree-identical to `88d1c84`.
The studies used development snapshots, principally `622975e`; they did not include
a published-1.0.0 artifact arm. The [baseline receipt](evaluation/coco-1.1.0/baseline.json)
verifies local source identity, not registry package contents. The future
compatibility task must pin the distribution too before making consumer claims.

| User need | Local tagged 1.0.0 baseline / inherited method | Experimental work already present | Intended 1.1.0 result, still to implement and verify |
| --- | --- | --- | --- |
| Understand where to start | Purpose-based catalog and common procedures | Explicit four stages and ten introductory skills | A release-integrated route with full specialist access and compatible direct requests |
| Keep control without unnecessary approval | Existing project/user authority rules | Manual awareness and one-spec automatic transitions with a before-push boundary | Consistent execution and resume boundaries; no repeated consent for an already selected action |
| Resolve material ambiguity | Focused interview, grilling and reuse procedures | Concrete question contract, with observed discovery/adherence failures | Relevant clarification reached and followed before unknown business behavior is adopted; known choices recovered and true unknowns safely pending |
| Hand work to another worker | Durable state and context procedures | Real fresh-context recovery and completed work in tested cases | Preserve those outcomes across release integration, including explicitly open choices and usable provenance |
| Receive a truthful completion report | Existing evidence and completion rules | Explicit original/actual/reason reporting, with observed misses and repairs | Final reports retain original assumptions and actual departures; missing runtime evidence stays pending |
| Use less ceremony | Conditional loading and small-work exceptions | Reuse and short-advice experiments; no established saving for tested rewrites | Keep working baseline behavior. Reduce only demonstrated redundant state or observed presentation friction |

The table states a direction, not a promise that every row needs more instructions.
For example, both returning-user controls already selected a focused next action.
The successful behavior should be preserved, not replaced merely to create a
visible 1.1.0 change. Compatibility of changed defaults remains to be assessed;
29 unchanged names alone cannot certify a minor release.

## A concrete expected experience

Illustrative target, not another measured trial: a user asks for a CSV importer.
The agent reads existing decisions, then asks whether ` A1 ` and `a1` identify
the same item if that material choice is genuinely unsettled. It explains a
counterexample, alternatives and its recommendation. It does not re-ask a recorded
answer or infer a hidden business choice from permission to implement.

The agreed behavior enters the existing spec and plan. The user can select the
next skill once or choose basic continuation for that spec. Implementation,
review and actual verification produce identifiable commits and a report of
original expectation, actual result and deviations. Another worker can recover
that state. If output policy remains unknown, it stays open; if a required browser
check cannot run, verification stays pending. Automatic flow ends before push.

This is the intended product: a reusable agreement about how work proceeds and
what its result must explain. The model may already perform many of these actions
without a skill. Packaging and maintaining a common contract is still a deliverable;
how much repeated human instruction it saves must be measured rather than assumed.

## Continue with a decision, not an endless benchmark

The next useful question is narrow: can a specific change prevent an observed
owner-decision mistake while preserving already successful recovery and reporting?
First make the measurement valid and check that the relevant procedure executes.
A file merely containing good advice does not close that gap.

State reduction needs an actual duplicated mutable source before a structural
intervention. Repeating stronger reuse prose is not a new result. Human advice
testing needs actual observed friction and a distinct presentation treatment;
the existing baseline must not be made artificially verbose. If neither problem
is observed, leave the behavior unchanged. Human participant availability does
not block unrelated correctness and authority work.

Keep a working baseline when a proposal adds no benefit. Reject efficiency claims
that miss their frozen threshold, report invalid measures as inconclusive, and
stop a scope that has no consequential unresolved decision. No repeated studies
are needed simply to produce a COCO win or justify the time already spent.

There is a defensible reason to continue: the work has built an attributable
package, clarified the team's policy, demonstrated bounded procedure delivery,
and withheld adoption of three unproven changes. There is also a limit: a small, explicit
task may need only the existing lightweight path, and economic return or easier
human learning is still unknown. 1.1.0 should earn its scope by making those
concrete contracts more reliable, with optional reductions only where justified.

# 실제 작업에 맞춘 브랜치·Jira 정리

동기화·충돌 해결·필수 검증을 마친 뒤, 최종 푸시 전에 적용한다. 이 절차는 실제 `coco-push` 실행 요청의 일부다. 스킬 설명·수정·검토 요청 자체로 사용자 저장소나 Jira를 변경하지 않는다.

## 실제 작업과 이름 비교

가져온 개발 기준 커밋과 최종 HEAD의 diff, 브랜치 고유 커밋, 연결 태스크의 요구·수용 조건을 함께 읽는다. 커밋 제목이나 마지막 수정 파일만으로 작업을 요약하지 않는다. 개발 기준에서 들어온 다른 사람의 변경을 이 브랜치의 새 작업으로 세거나, 되돌린 변경·미완료 요구를 구현한 것으로 쓰지 않는다. 미커밋 사용자 파일은 푸시할 작업에 섞지 않는다.

브랜치명의 작업요약이 실제 핵심 목적·범위를 나타내는지 판단한다. 작은 내부 구현 변경이나 표현 취향 때문에 적절한 이름을 다시 짓지 않는다. 다른 기능을 나타내거나 중요한 범위가 빠졌다면 실제 변경에 근거한 새 요약과 수정 이유를 정리한다. 작업 범위 자체가 불명확하거나 여러 무관한 태스크가 섞였으면 이름만 바꿔 정당화하지 말고 필요한 결정을 확인한다.

## 대상과 변경안 확인

- 태스크 기록·티켓 링크·PR·명시 요청에서 **전체 Jira 키**와 프로젝트를 확인한다. 브랜치의 숫자만으로 프로젝트를 추측하거나 동명의 다른 티켓을 고르지 않는다. 현재 Summary와 Description, 연결 관계를 실제로 읽는다. 필요한 정보나 읽기/쓰기 기능이 없으면 수정안을 남기고 필요한 부분만 확인한다.
- 이름은 [coco-build의 명명 규칙](../../coco-build/SKILL.md#기능-브랜치-준비)을 따른다. 종류·파트·태스크번호를 유지하고 작업요약 부분만 실제 작업에 맞게 바꾼다. 다른 태스크나 파트로 바꿀 필요가 있으면 별도 범위 결정을 확인한다. 최종 브랜치 요약과 Jira Summary는 같게 맞춘다. Git에서 허용하지 않는 문자의 표기는 해당 명명 규칙대로 확인한다.
- Description에는 이번 브랜치의 실제 변경·검증한 내용·남은 범위를 반영한다. 기존 요구사항·수용 조건·링크·다른 사람의 기록을 보존하며, 관련 작업설명 부분만 수정하거나 명확한 이번 브랜치 작업 구역을 추가한다. 전체 설명을 자동 생성 요약으로 덮어쓰거나 미완료 요구를 지우지 않는다. 이미 같은 구역이 있으면 갱신하고 중복 추가하지 않는다. 실제 필드가 서식 있는 문서이면 지원되는 형식으로 편집해 기존 서식을 보존한다.

새 이름은 `git check-ref-format --branch`로 검사하고 로컬·원격 충돌 여부를 조회한다. 같은 이름의 다른 브랜치를 덮어쓰거나 `-M`으로 개명하지 않는다. 새 원격 이름이 이미 있으면 동일 태스크인지 확인하고, 미반영 커밋이 있으면 통합 절차로 돌아가 검증·요약을 다시 수행한다. 관계가 불명확한 충돌은 필요한 결정을 확인한다.

개명 전에 기존 로컬 이름·HEAD·업스트림·원격 ref/OID, 새 이름과 최종 쓰기 목적지를 기록한다. **기존 원격 작업 브랜치의 고유 커밋을 먼저 가져와 통합**한다. 이름을 바꾸면서 기존 원격 작업을 읽지 않고 건너뛰지 않는다. 기본 푸시 ref는 새 이름으로 맞춘다. 사용자가 다른 이름의 목적지를 명시했다면 그 요청을 조용히 바꾸지 말고 필요한 목적지 결정을 확인한다.

## 변경과 확인

1. 비교·관련 정보·Git 후보·목적지가 확정되면 `git branch -m <새이름>`으로 현재 작업 브랜치를 개명한다. 인수는 안전하게 전달한다. HEAD·사용자 파일은 유지됐는지 확인한다. 기존 승인 범위 안의 이름·필드 수정 때문에 같은 승인을 다시 요구하지 않는다.
2. Jira를 쓰기 직전에 다시 읽는다. 처음 읽은 뒤 다른 사람이 바꿨으면 최신 내용을 바탕으로 관련 부분만 합치고, 충돌하는 의도가 있으면 그 결정만 확인한다. 지원되는 버전/조건부 갱신 기능이 있으면 사용한다. 확인한 티켓의 Summary와 Description만 갱신한다. 상태 전이·완료 처리·담당자·우선순위·댓글 작성은 포함하지 않는다.
3. Jira를 재조회해 새 Summary와 작업설명이 실제로 반영됐고 보존할 내용이 남았는지 확인한다. 응답이 유실됐으면 재조회부터 하며 중복 쓰기나 성공 추정을 하지 않는다. 권한·필드 제한·네트워크 실패를 우회하지 않는다.
4. 최종 HEAD와 원격 ref를 다시 확인한 뒤 동기화 절차의 단일 refspec으로 **최종 이름의 브랜치**를 일반 푸시한다. 그 사이 통합할 커밋이 생기면 재검증·요약 대조를 수행하고 설명도 달라진 실제 작업에 맞춘다. 원래 절차의 갱신·통합/푸시 각 3회 한도를 유지한다.

로컬 개명·Jira 갱신·원격 푸시는 하나의 원자적 작업이 아니다. Jira 갱신이나 재조회가 실패하면 푸시하지 않고, 이미 바뀐 로컬 이름과 미반영 티켓 상태를 구분해 남긴다. Jira 갱신 뒤 푸시가 실패해도 완료로 보고하지 않는다. 자동 원복으로 다른 사람의 기록을 덮어쓰지 말고 재개 시 실제 상태부터 확인해 완료된 단계를 반복하지 않는다.

새 ref를 게시했다고 기존 원격 ref가 개명되거나 삭제된 것은 아니다. 기존 원격 브랜치는 남기고 새·옛 ref와 PR 연결 영향을 보고한다. 필요한 PR 수정·원격 삭제는 별도 요청 범위다. 로컬 업스트림이 옛 작업 ref를 가리키면 최종 목적지와의 차이를 확인해 보고하며, 업스트림만 믿고 옛 이름이나 개발 기준에 푸시하지 않는다.

# coco-build의 Jira 브랜치 규칙 확인

기존에는 기능 브랜치와 작업별 커밋만 정했다. 사용자 요청에 따라 새 구현 브랜치는 `종류(파트)/지라태스크번호-한글작업요약`으로 만들고, 작업요약은 실제 Jira 태스크의 제목/Summary와 같게 사용하도록 추가했다. 정확한 명명 규칙은 `coco-build/SKILL.md`가 소유하며 공통 계약과 고급 구현 절차는 이를 참조한다.

## 실제 Git 확인

[명령·결과](build-branches.json)는 독립된 임시 저장소에서 실행했다. 모든 Git 인수는 문자열 배열로 전달했고 전역 Git 설정·실제 프로젝트 원격·실제 Jira는 사용하지 않았다. 확인 후 임시 저장소를 제거했다.

| 사례 | 관찰 결과 |
|---|---|
| `TEAM-123`, 요약 `OAuth2.0_구글`, `feat`·`be` | `feat(be)/123-OAuth2.0_구글`의 형식 검사·생성·다시 읽기 성공. 요약과 브랜치명이 정확히 일치 |
| 다른 종류·파트와 한글 요약 | `fix(fe)/126-구글_로그인_오류` 생성·다시 읽기 성공. 예시의 종류·파트에 고정하지 않아도 유효 |
| 요약에 공백 포함 | 읽기 전용 `check-ref-format --branch`가 실패. 기존 브랜치·ref·사용자 파일 유지 |
| 요약에 콜론 포함 | 같은 검사에서 실패. 임의로 요약을 변환하지 않았고 기존 상태 유지 |
| 이미 존재하는 브랜치 이름으로 생성 시도 | Git이 거절. 기존 ref·현재 브랜치·사용자 파일 유지 |

성공 경로에서도 기준 HEAD, 미추적 사용자 메모의 바이트, Git 상태가 유지됐다. Git 자체의 거절은 스킬이 언제나 올바르게 재사용·질문한다는 증명은 아니다.

## 지침 검토 범위

작성자가 확인한 입력 분기는 다음과 같다. 이 부분은 실제 에이전트 대화 시험이 아닌 지침 검토다.

- 태스크 정보가 이미 제공됐으면 다시 묻지 않는다. 번호·요약 등 필요한 정보가 없으면 임의의 대체값을 만들지 않는다.
- 실제 태스크의 Summary를 사용하며 에픽 제목·설명에서 만든 요약·영문 슬러그로 바꾸지 않는다.
- Git이 허용하지 않는 요약이면 원문과 최소 변환안을 보여주고 표기를 확인한다. 공백을 밑줄로 자동 치환하지 않는다.
- 같은 태스크의 기존 작업 브랜치가 형식과 다르면 처리 방향을 확인한다. 새 작업을 기준 브랜치에서 시작하는 경우와 구분하고 기존 브랜치를 자동 개명·삭제하지 않는다.
- 새 브랜치 준비 외 구현·검증·작업별 커밋·완료 상태의 기존 책임을 유지한다.

실제 Jira 조회·호스트별 브랜치 제한·독립 에이전트의 질문 행동을 검증한 것으로 확대하지 않는다. 원본의 `essential_rules`, 고정 원문·체크섬은 유지하고 팀 추가 규칙임을 결정 기록과 대응표에 명시했다.

## 패키지 검사

`python3 scripts/validate.py`, 기존 자동 검사 23개, 공식 `skill-creator/scripts/quick_validate.py skills/coco-build`, `git diff --check`가 통과했다. 원본 대응표의 `essential_rules`와 고정 manifest가 시작 커밋과 같은지도 별도로 비교했다.

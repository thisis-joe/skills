# COCO 스킬 대기 시간 진단

2026-10-21에 실제 사용 기록과 비교 실험으로 COCO 스킬이 왜 오래 걸리는지 확인했습니다. 이 문서는 1차 조정(`feat/skill-latency-wave-1`)의 판단 근거입니다. 표본이 작으므로 결론은 "측정된 범위에서"라는 단서를 붙여 읽습니다.

## 질문

1. 시간은 어디에 쓰이는가?
2. 불필요하게 많이 살펴보거나, 이미 한 일을 반복하는가?
3. 세 원저자(Addy Osmani, Matt Pocock, Lauren Tan의 pstack)의 내용을 따르는 것이 대기 시간을 요구하는가?
4. 코드와 산출물이 불필요하게 길어지는가?
5. 어느 정도의 대기는 감수할 만한가?

## 방법

| 조사 | 대상 | 방식 |
|---|---|---|
| 실제 기록 분석 | 한 사용자의 Claude Code 세션 기록 중 coco 스킬 호출 11회 (push, merge, ship, docs, updateskill 3회, start 2회, tellmeskill 2회) | 호출별 시간표를 만들고 각 구간을 필수 / 스킬이 요구했지만 효과 낮음 / 반복 / 과잉 검증 / 오류 재시도 / 앱 부가 작업으로 분류. 원인이 된 지시문 위치를 인용 |
| 문서 구조 분석 | 29개 스킬과 `_coco-shared` | 호출마다 반드시 읽는 바이트, 조건부 읽기의 조건 명확성, 순차 단계 수, 중복 규칙, 출력을 길게 만드는 규칙 |
| 원저자 대조 | `sources/addy`, `sources/matt`, `sources/pstack` | 원저자의 길이·속도 지침과 COCO가 더 엄격해진 지점 |
| 비교 실험 | 리뷰, 리서치, 작은 구현 3과제 × (스킬 사용 / 미사용) | 같은 지시로 각 1회 실행, 결과를 가린 채 판정 에이전트가 저장소로 직접 검증해 채점 |
| 개선안 평가 | 지연 우선 / 가치 우선 / 구조 우선 3개 안 | 관점이 다른 판정 3개와 반박 전담 1개 |

측정 정의([measure_sessions.py](measure_sessions.py)):
- **실행 시간**: 스킬 호출부터 다음 사람 메시지 직전의 마지막 모델 응답까지. 행 사이 간격은 120초까지만 셉니다. 백그라운드 작업이 끝나 같은 작업이 이어지면 그 시간도 포함합니다.
- **모델 호출**: API 메시지 id 기준으로 중복을 제거한 횟수. 스킬을 고르는 호출은 포함하지 않습니다.
- **출력 토큰**: 생각(thinking)을 포함한 출력 토큰. 생각 내용은 기록에서 가려져 있어 토큰 수로만 추정합니다.
- **도구 시간**: 도구 호출부터 결과까지. 명령 실행, 네트워크, 서브에이전트 대기를 포함합니다.
- 세션 기록은 개인 데이터라 저장소에 넣지 않습니다. 이 문서에는 집계값만 적습니다.

## 결과 1. 시간은 대부분 모델 생성과 호출 횟수에 쓰인다

도구 시간은 실행 시간의 3~33%(중앙값 17%)였습니다. 나머지는 모델이 생각하고 답을 쓰는 시간(초당 약 80~110토큰)과, 모델 호출 한 번마다 붙는 5~10초입니다.

| 스킬 | 작업 | 실행 시간 | 모델 호출 | 출력 토큰 | 도구 시간 비율 | 같은 안전성으로 줄인 경로 추정 |
|---|---|---:|---:|---:|---:|---:|
| coco-push | GitLab 브랜치 동기화, Jira 기록, push | 104초 | 9 | 7.2k | 19% | 약 62초 |
| coco-merge | GitHub PR 머지 | 110초 | 8 | 3.6k | 23% | 약 50초 |
| coco-ship | PR 출시 준비 판정 (NO-GO) | 74초 | 9 | 5.9k | 19% | 약 50초 |
| coco-docs | README 재작성 (독립 리뷰 대기와 수정 포함) | 611초 | 43 | 48.4k | 17% | 약 250~300초 |
| coco-updateskill | coco-push에 draft PR 생성 추가 | 1,252초 | 66 | 97.3k | 12% | 약 350~450초 |
| coco-updateskill | 전용 worktree 규칙 추가 | 639초 | 47 | 37.3k | 12% | 약 180초 |
| coco-updateskill | 문구 수정 (spec/ADR 기본 경로) | 108초 | 14 | 5.8k | 26% | 약 78초 |
| coco-start | 다음 작업 고르기 (skills 저장소) | 147초 | 13 | 12.2k | 33% | 약 30초 |
| coco-start | "뭐하지?" (다른 프로젝트) | 61초 | 7 | 4.4k | 13% | 약 41초 |
| coco-tellmeskill | 전체 목록 출력 | 53초 | 4 | 6.0k | 9% | 약 20초 |
| coco-tellmeskill | 최근 스킬 메뉴 | 26초 | 3 | 2.4k | 3% | - |

- push는 자연어 요청이라, 위 시간 전에 스킬을 고르는 호출이 33초(3.6k 토큰) 더 있었습니다. 사람 메시지부터 재면 약 140초입니다.
- start 147초 실행의 도구 시간 33%는 대부분 경로를 정하는 데 필요 없던 테스트와 머지 미리보기였습니다.

## 결과 2. 같은 과제에서 스킬은 23~30% 더 걸렸고 품질은 비슷했다

에이전트 기록의 첫 행부터 마지막 행까지 잰 시간입니다.

| 과제 | 스킬 사용 | 미사용 | 모델 호출 | 판정 |
|---|---:|---:|---|---|
| 커밋 리뷰 (README 갱신) | 219초 | 178초 | 25 vs 18 | 미사용이 나음. 공개 npm 페이지에 "미출시" 문구가 실리는 위험을 미사용 쪽만 찾음. 스킬 쪽은 절차 설명(스냅샷 해시, 축 표)으로 길어짐 |
| 코드 리서치 (dev/develop 선택) | 67초 | 52초 | 10 vs 7 | 스킬이 근소하게 나음. 미사용 쪽은 문서에 없는 우선순위를 사실처럼 씀 |
| 작은 구현 (`validate.py --json`) | 193초 | 149초 | 19 vs 14 | 무승부. 제품 코드 +8줄 vs +7줄, 둘 다 테스트 통과 |

- 스킬 쪽은 지시문 때문에 문맥이 7~16k 토큰 늘었고, 모델 호출이 5~7번 늘었습니다. 늘어난 시간의 대부분은 이 호출 횟수입니다.
- 구현 과제의 스킬 실행은 공용 계약과 `advanced/build.md`를 한 호출로 읽고, 브랜치 이름 검사와 추가 검증 명령을 실행했습니다. coco-review는 따로 부르지 않고 diff로 직접 검토했습니다.
- 과제당 1회씩이라 오차가 큽니다. 다른 기록에서 단일 API 지연이 31~36초 나온 적이 있어, 한 번의 실행으로 비율이 뒤집힐 수 있습니다.

## 결과 3. 원인

공통 원인 순서입니다. 비율은 분석한 실행들의 합계 기준이며, 호출 빈도로 가중하지 않았습니다. updateskill과 docs는 드물게 쓰이지만 합계에서 큰 비중을 차지합니다.

### 3.1 변경 크기와 무관한 검증 (합계의 약 45%, updateskill·docs에 집중)

- `coco-updateskill/SKILL.md:28`의 "Use a fresh context for important changes"에서 "important"가 정의되어 있지 않습니다. 같은 스킬이 이 판단 하나로 108초(문구 수정) 또는 639~1,252초(절차 변경)가 걸렸습니다.
- worktree 규칙 추가에서는 시간의 약 62%(약 431초)가 결함을 찾지 못하고 아무것도 바꾸지 않은 평가였습니다.
- 128줄짜리 스킬 변경에 평가 코드 819줄, 111개 파일·2,815줄 평가 커밋(22배)이 따라왔습니다. 49줄 테스트는 바뀐 규칙이 아니라 Git 자체의 동작과 바뀌지 않은 설치기를 확인했습니다.
- coco-docs에는 길이 기준이 없습니다(`coco-docs/SKILL.md:24` "at the depth the reader needs"). README가 2.7배(바이트 기준)로 커졌고, 쓰기 시간도 그만큼 늘었습니다.
- 그 실행에서 에이전트가 스스로 붙인 독립 리뷰가 실제 오류 2개를 찾았습니다. 둘 다 설명 대상 스킬 문서를 끝까지 읽지 않아 생긴 오류였습니다. coco-docs 자체에는 독립 리뷰 단계가 없습니다.

### 3.2 정해진 Git·forge 단계를 모델이 직접 쓰는 비용과 셸 오류 재시도 (push·merge·start 시간의 30~40%)

- 단계마다 모델 호출이 하나씩 붙습니다. 검사 자체는 한 명령으로 묶으면 3초도 걸리지 않았습니다(push의 fetch, 조상 확인, 충돌 표시 검사, push 직전 재확인, 원격 확인 합계).
- zsh에서 `"$V:refs/..."`의 `:r`이 수정자로 해석되어 push가 한 번 실패했습니다(재시도 13초). 스킬 문서에는 셸 주의사항이 없습니다. PowerShell도 `$V:refs`를 드라이브 한정 변수로 읽으므로 같은 문제가 생깁니다.
- ship에서 `echo ======`가 zsh의 `=` 확장으로 실패해 출력이 사라지고 다시 실행했습니다.
- `merge_preflight.py`처럼 스크립트로 옮긴 단계는 2.7초 한 번으로 끝났고, 참조 문서를 읽지 않고도 안전하게 머지했습니다.

### 3.3 출력량 (합계의 약 10~15%, 짧은 스킬에서는 최대 비중)

- 보고 항목 나열: coco-push 약 23개, coco-merge 약 15개, coco-updateskill 13개. push 보고는 950토큰이었는데 필요한 내용은 약 350토큰이었습니다.
- coco-start가 설정 요청이 아닌데도 품질 기준 표를 출력했습니다(2,707자).
- coco-tellmeskill은 60개 전체 목록(4,012자, 약 27~39초)을 출력했고, 그중 32개는 COCO가 아닌 스킬이었습니다.
- 반대 근거: merge 보고(324자)는 충분했고, ship 판정은 너무 짧아 사용자가 "무슨 뜻이냐"고 다시 물었습니다. 줄이되, 막힌 이유는 한 문장으로 꼭 설명해야 합니다.

### 3.4 범위를 벗어난 일과 반복 (합계의 약 5~8%, start에서 최대 45%)

- coco-start가 다음 경로만 정하면 되는데 머지 미리보기, diff 읽기, 테스트 실행까지 했습니다(147초 중 약 64초).
- coco-start가 CI 존재 여부를 세 번 확인했습니다(두 기록 모두).
- coco-ship은 출시를 막는 문제를 찾은 뒤에도 CI가 이미 통과시킨 audit을 다시 실행했습니다. `contracts.md:19`의 "통과한 검사 재사용" 규칙과 어긋납니다.
- coco-docs 요청에서 같은 설치 시나리오를 메인 에이전트와 리뷰 에이전트가 두 번 실행했고, 같은 문서를 연속으로 두 번 읽었습니다.
- coco-merge 확인 명령이 `gh pr view`를 두 번 호출했습니다.

### 3.5 호출마다 붙는 고정 비용 (합계의 약 3~5%)

- 23개 진입점이 "Read the common contract before acting"(8.5KB)으로 시작합니다. 그중 약 27%는 다른 스킬의 소유 규칙입니다.
- "If any applies or is unclear, read the advanced modes"의 조건은 대부분 거의 항상 참이라 고급 문서를 결국 읽게 됩니다.
- 첫 명령과 묶으면 추가 비용은 1초 미만이지만, 따로 읽으면 모델 호출이 하나 늘어납니다(ship: 9번 중 2번, 약 7.5초).

### 3.6 COCO 밖의 원인 (합계의 약 3~5%)

- 자연어로 요청하면 스킬을 고르는 호출이 먼저 생깁니다(push에서 33초). 다만 그 안에 작업 계획도 들어 있어, `/coco-push`로 직접 호출해도 전부 사라지지는 않습니다. 33초는 상한입니다.
- 데스크톱 앱의 마무리 도구(약 11초)와 요청하지 않은 후속 세션 제안(13~14초).
- 원인을 알 수 없는 API 지연(31초 1회).

## 결과 4. 원저자들은 COCO보다 가볍다

| 원저자 | 원래 방식 | COCO에서 사라진 것 |
|---|---|---|
| Matt | 스킬이 짧음(구현 103단어, 리서치 131단어, 중앙값 530단어). 큰 절차는 사용자가 직접 입력해야만 실행. 여러 세션이 아닌 일은 스펙·티켓 없이 바로 구현 | 공통 계약 선행 읽기가 원본에 없음. 가벼운 경로가 "정적 수정"으로만 좁아짐. PR 본문 지침(짧게, 서론 없이)이 7개 절 양식으로 바뀜 |
| pstack | 56개 중 55개가 직접 호출 전용. 작업에 맞춰 모델과 추론 강도를 낮추라고 함. 서브에이전트는 기본적으로 백그라운드 실행. PR 본문은 1분 브리핑(약 40줄 이하) | 강도 조절 지침이 없음("Do not hardcode model choices"만 있음). 사소한 스킬 수정의 빠른 경로가 사라짐 |
| Addy | 스킬마다 "이럴 때는 쓰지 마라"가 있음. "모든 작업에 모든 스킬이 필요하지는 않다". 참조 문서는 필요할 때만 읽음. ship에 작은 변경 생략 기준 | 스킬별 생략 조건이 하나의 좁은 가벼운 경로로 합쳐짐. "크기와 대상은 필수 검사를 면제하지 않는다"가 공통 규칙으로 일반화됨 |

결론: 원저자를 따르기 때문에 느린 것이 아니라, 세 원저자의 규칙을 합치면서 각자가 둔 생략 규칙이 빠져 느려졌습니다.

## 결과 5. 코드 길이

- **제품 코드는 길어지지 않았습니다.** 같은 구현에서 COCO 사용 +8줄, 미사용 +7줄이었고, 불필요한 import는 오히려 미사용 쪽에 있었습니다. "최소 구현", "실제 재사용 전에는 추상화 금지", "리팩터링 분리" 규칙이 코드를 짧게 유지합니다.
- **코드 주변의 글은 길어졌습니다.** 보고서(push 950토큰), 문서(README 2.7배), 평가 산출물(22배), Git 자체의 동작을 확인하는 테스트, 원래 SKILL.md보다 1.6배 긴 `pull-request.md`(11.7KB, push가 PR 단계에서 매번 읽음).
- 한계: 근거는 8줄짜리 Python 변경 1건뿐입니다. TypeScript 형식 규칙이나 API 설계 규칙의 영향은 측정하지 않았습니다.

| 머지할 head 커밋 고정, 대기열 진입과 머지 완료 구분, 머지 후 대상 브랜치 포함 확인 | merge 스크립트로 2.7초 |

| 새 테스트가 의도한 이유로 먼저 실패하는지 확인, 실패 테스트를 지우거나 기준을 낮추지 않기 | 원저자 공통, 비용이 작음 |
| 사용자 변경 보존, 작업 파일만 스테이징 | 전용 worktree 규칙(약 12초)이 다른 세션의 미커밋 작업을 지킴 |
| merge의 리뷰 댓글 본문 읽기 | 대화 해결을 요구하지 않는 저장소에서는 CLEAN 상태여도 중요한 지적이 남을 수 있음. 실제로 그 기록의 댓글 2개가 후속 작업이 됨 |
| 안전 계열(ship, security, migrate, build, debug, review, verify, automate 등)의 "애매하면 고급 문서 읽기" | 결정 기록상, 모호한 조건이 모드를 건너뛰게 만든 사례 때문에 생긴 규칙 |

## 목표 대기 시간

감수할 대기는 실제 증거를 만드는 시간(테스트, 실행 점검, 네트워크)입니다. 절차를 위한 절차, 반복, 긴 보고는 줄입니다.

| 작업 | 현재 | 목표 |
|---|---|---|
| 스킬 목록·설명 | 26~53초 | 30초 이내 |
| 다음 작업 고르기 (start) | 61~147초 | 45초 이내 |
| push (충돌 없음) | 104초 (사람 메시지부터 140초) | 60초 이내, draft PR 포함 90초 이내 |
| merge (깨끗한 PR, 체크 대기 제외) | 110초 | 50초 이내 |
| ship (PR 준비) | 74초 | 60초 이내, 실행 점검이 있으면 2~4분 |
| 리뷰 1건 | 173~219초 | 90초 이내 |
| 작은 구현 1단위 | 2~3분 | 2~3분 (테스트 시간이 바닥) |
| 문서 수정 / README 재작성 | 611초 | 60초 이내 / 5분 이내 |
| 스킬 문구 수정 / 절차 변경 | 108초 / 11~21분 | 2분 이내 / 5분 이내 |

## 한계와 미확인 사항

- 실제 기록 11회는 한 사람의 기록이며, 대부분 이 저장소의 스킬 정비 작업입니다. 일부는 지금보다 짧았던 이전 버전의 스킬로 실행됐습니다(contracts.md 6.6KB → 현재 8.5KB).
- coco-build, coco-review, coco-debug, coco-verify의 실제 사용 기록은 없습니다.
- 비교 실험은 과제당 1회, 판정자는 1명(LLM)입니다.
- 생각 내용이 가려져 있어, 지시문이 생각을 늘린다는 주장은 토큰 수에서 추론한 것입니다.
- 안전 장치가 실제로 얼마나 자주 작동하는지(동시 push, dev/develop 동시 존재 등)는 성공 기록만으로는 알 수 없습니다.
- 측정은 macOS의 zsh에서만 했습니다. Windows 셸 동작은 [실험 조건](protocol.md)의 CI 실행으로 따로 확인합니다.
- 그래서 개선 후 동작 확인과 재측정을 하고, 반복 비교 실험(과제당 3회, 판정 순서 교차)은 후속 분석에서 합니다.

## 재현

- 기록 분석: `python3 docs/evaluation/latency/measure_sessions.py --project <폴더> --since <시각> --until <시각>`이 지정한 범위의 스킬 호출별 실행 시간, 모델 호출 수, 출력 토큰, 도구 시간을 계산합니다. 본문, 인자, 경로는 출력하지 않고 세션은 해시로만 표시합니다. 위 표는 2026-10-20~21 범위를 4개 프로젝트에 대해 실행한 결과입니다.
- 비교 실험과 동작 확인: [protocol.md](protocol.md)에 과제, 실행 조건, 격리 방법, 판정 기준을 고정합니다.

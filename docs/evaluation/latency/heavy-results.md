# 무거운 네 스킬 조정의 동작 확인과 재측정 결과

[진단](heavy.md)에 따라 바꾼 coco-build, coco-review, coco-debug, coco-verify를 조정 전 사본과 같은 예제에서 짝지어 실행했습니다. 2026-10-22 결과입니다.

## 실행 방식

| 항목 | 내용 |
|---|---|
| 비교 대상 | kit-a: 조정 전 `origin/main`(d2d848d)의 `skills/`. kit-b: 1차 조정본(7d83f82). kit-c: kit-b에 강화 작업 리뷰 경로 수정을 더한 최종본(35fac2e, 아래 "추가 수정"). 모두 `git archive`로 고정 |
| 실행 | [실험 조건](protocol.md)의 "경로 실행". 에이전트가 Skill 도구 없이 사본의 `SKILL.md`를 읽고 링크를 따라감. 전역 설치본은 읽지 않게 함 |
| 예제 | [진단](heavy.md)의 기준 측정과 같은 4개 저장소를 새로 복제 |
| 반복 | 시나리오마다 사본당 2회, build 두 시나리오는 3회. build 로그인은 확인 묶음 2+2회를 더 돌림. 같은 시나리오의 비교 대상은 같은 시각에 시작해 부하 차이를 같게 함 |
| 측정 | 에이전트가 처음과 마지막에 찍은 `date +%s`. 모델 호출 수와 도구 시간은 에이전트 기록에서 셈 |
| 판정 | 시나리오마다 새 문맥의 판정 에이전트 1명. a·b·c가 무엇인지 알리지 않음. 모든 실행에 같은 변이와 같은 실서버 점검을 적용 |
| 환경 | claude-opus-5-5, Claude Code 2.1.304, macOS, Python 3.9.6 |

측정 지시문은 결과와 별도로 실행 기록(시각, 커밋, 읽은 COCO 문서)을 붙이게 했습니다. 기준 측정처럼 결과 본문에 "사용한 스킬"을 쓰게 하지 않아, 그 부분의 차이는 생기지 않습니다.

- debug와 verify는 양쪽 범위가 겹치지 않습니다. review와 build 조기 종료의 7%는 오차 범위입니다.

## 행동 변화

| 시나리오 | 조정 전 | 조정 후 |
|---|---|---|
| debug | 수정 단계에서 coco-review, review.md, verify.md까지 읽음(2/2, COCO 문서 6~8개). 범위 수집기 실행 1/2 | coco-build 진입 문서만 읽음(2/2, 4개). 수집기 0/2 |
| build: 조기 종료 | review.md와 수집기를 매번 사용(3/3, 문서 6~7개). 조기 종료가 기본 데이터에서 작동 2/3 | review·verify 문서와 수집기 없음(3/3, 문서 3~4개). 조기 종료 작동 3/3(1회는 최소 개선 폭을 두어 작동시키고 사용자 결정으로 보고) |
| build: 로그인 기능 | review.md·verify.md 읽음(5/5). 테스트 해시 비용을 낮춘 실행 3/5, 운영값을 고정하는 테스트 1/5. 나머지 2회는 모든 테스트가 운영값으로 해시해 한 번에 9~14초 | 인증 작업을 강화 작업으로 보고 review.md를 읽음(5/5). 테스트 해시 비용을 낮추고 운영값을 고정(5/5), 한 번에 2.5~3.1초 |
| review | 정확한 범위인데 수집기 실행(2/2), Limitations 절(2/2) | `git diff`와 `git status`만 사용(2/2), 결과부터 제시, Limitations 절 없음 |
| verify | 구동 스크립트와 증거 파일 작성(2/2) | curl 즉석 요청, 서버 기록만 남김(2/2). 요청한 주장마다 판정 하나 |

## 결과 품질 (가린 판정)

| 시나리오 | 판정 | 근거 |
|---|---|---|
| review | 결과 같음, 읽기 쉬움은 조정 후가 나음 | 4회 모두 심은 결함 3개를 정확한 줄로 찾음, 거짓 지적 없음, 파일 변경 없음, 같은 추가 결함 2개(큰 page 값 연결 끊김, 빈 값 무시). 사용성 점수 3, 3 → 4, 4 |
| verify | 결과 같음, 조정 후가 약간 나음 | 4회 모두 3/3, 거짓 주장 없음. 조정 후 2회 모두 검색과 페이지가 겹치는 영향을 보임. 조정 전 1회는 머리말 개수가 표와 맞지 않음 |
| debug | 조정 후가 나음(2회씩이라 단서 필요) | 4회 모두 심은 결함 2개 수정, 새 테스트가 원래 코드에서 실패, 정확도 테스트 20/20 통과. 평가가 저장된 스케일러 대신 다시 학습하는 문제를 조정 후 2/2, 조정 전 1/2만 고침. 고치지 않은 조정 전 실행은 그 변이를 잡지 못했고(2/3) 커밋별 테스트 수를 틀리게 적음 |
| build: 조기 종료 | 같음 | 판정한 4회 모두 요구 충족, 같은 변이 5개 중 4개 검출(같은 생존 변이: 동률을 개선으로 셈). 실행 간 차이가 변형 간 차이보다 큼 |
| build: 로그인 기능 | 제품 동작과 보안 점검은 같음, 테스트 품질은 조정 후가 나음 | 10회 모두 요구 충족, 요청 변이 3/3. 보안 점검 통과율은 조정 전 40%, kit-b 44%, kit-c 50%로 각 사본 안의 편차보다 작음. 추가 변이 검출은 조정 전 21/25, kit-b 14/15, kit-c 10/10이며 조정 전이 놓친 것은 모두 해시 비용을 낮춘 변이 |

build 로그인 보안 점검의 세부입니다(로그인 CSRF 차단 / 깨진 이웃 쿠키와 CVE-2024-7592 지연 회피 / 짝 없는 서로게이트 400).

| 사본 | CSRF 차단 | 쿠키 직접 파싱 | 서로게이트 처리 | 쿠키 없는 로그아웃에 삭제 쿠키 없음 |
|---|---|---|---|---|
| 조정 전 (5회) | 2 | 3 | 1 | 0 |
| kit-b (3회) | 1 | 1 | 2 | 0 |
| kit-c (2회) | 1 | 1 | 1 | 1 |

- 기준 측정의 build 실행이 찾은 세 가지는 이번에도 위협 점검과 자기 검토에서 나왔고, 조정 전후 모두 일부 실행에서만 나왔습니다.
- 자기 검토 중에 실제 결함을 고친 실행은 조정 전 3회(쿠키 파싱 3, 로그인 CSRF 1), 조정 후 1회(로그인 CSRF)였습니다. 조정 후 쿠키를 직접 파싱한 2회는 검토에서 고친 것이 아니었습니다(보고에 검토 수정으로 나오지 않음).
- 집계 단계의 실수로 판정자 일부가 결과 보고를 늦게 받았습니다. debug와 build 로그인 판정자는 받은 뒤 다시 확인했고, build 조기 종료 판정자는 3회의 보고 대신 커밋 메시지와 README로 확인했습니다. 판정의 중심은 저장소 상태와 실서버 점검입니다.

## build 로그인 과제가 kit-b에서 느려진 이유

| 실행 | 시간 | 늘어난 곳 |
|---|---|---|
| kit-b 1 | 719초 | 요청하지 않은 Python 3.12 전체 실행(74초)과 개발 모드 실행 두 번(41·45초). 도구 시간 209초 |
| kit-b 2 | 602초 | 뚜렷한 원인 없음. 같은 묶음 조정 전 범위(532~573초)에서 약 30초 위 |
| kit-b 3 | 666초 | 실서버 점검에서 서버가 멈춰 도구 호출 하나가 121초. 리뷰 구간 99초(같은 묶음의 조정 전 실행 67초) |

지시문 때문인 비용은 리뷰 경로 하나였습니다. "강화 작업은 coco-review"라는 문장이 진입 문서 하나를 더 읽게 했고, 1회는 diff를 끝낸 뒤에야 읽었습니다.

### 추가 수정

강화 작업과 의존성·공유 계약 변경은 coco-review 대신 리뷰 모드(review.md)와 수집기를 쓰고, 처음부터 강화 작업이면 고급 build 문서와 함께 읽게 바꿨습니다(35fac2e). 새 문맥·요청된 리뷰만 coco-review로 갑니다. 확인 묶음에서 kit-c 2회는 둘 다 고급 build 문서 바로 다음(시작 후 16초)에 review.md를 읽었고, 같은 시각의 조정 전 2회와 시간이 같았습니다.

## 기준 대비

| 기준([실험 조건](protocol.md)) | 결과 |
|---|---|
| 저장소 검사 | `scripts/validate.py`와 unittest 127개 통과 |
| 안전 구분을 잃은 경우 없음 | 없음. build·debug 실행 모두 실패 테스트를 먼저 확인하고 실행 점검과 자기 검토를 했으며, verify·review는 심은 결함을 모두 찾음 |
| 어떤 과제도 10% 넘게 느려지지 않음 | 최종본 기준 통과. debug −33%, verify −26%, review +7%, build 조기 종료 +7%, build 로그인 −2%(확인 묶음). kit-b는 build 로그인에서 +20%였고, 원인 중 지시문 탓인 리뷰 경로를 최종본에서 고침. 최종본의 build 로그인 측정은 2회뿐 |

## 한계

- 사본당 2~3회(build 로그인 조정 전 5회)입니다. 같은 사본 안에서도 287~432초, 532~723초처럼 차이가 커서 10~20% 차이는 오차 범위로 봅니다.
- kit-c(최종본)를 따로 돌린 것은 build 로그인 2회뿐입니다. kit-b와 kit-c의 차이는 coco-build 진입 문서의 문장 하나라서, 다른 시나리오의 kit-b 결과를 최종본 결과로 봅니다.
- 동시에 12~20개 실행을 돌려 부하가 컸고, 실행 하나는 멈춘 서버로 121초를 잃었습니다.
- 판정자는 LLM 1명입니다. 예제는 작은 Python 저장소뿐이고, 사람이 중간에 답하는 정상 사용은 측정하지 않았습니다.

## 재현

- 각 실행은 "사본의 `skills/coco-<name>/SKILL.md`를 읽고 따르라, Skill 도구와 다른 사본은 쓰지 말라"는 문장과 [진단](heavy.md)의 과제 문장을 받습니다.
- 집계는 에이전트 기록에서 메시지 id 기준 모델 호출 수, 도구 호출부터 결과까지의 시간, 실행 기록의 `date +%s`를 씁니다. 실행 기록과 판정 원문은 개인 작업 폴더에만 두고 저장소에는 집계값만 적습니다.

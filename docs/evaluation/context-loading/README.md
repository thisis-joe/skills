# 조건부 로딩 분할의 보존 검사와 제한된 적용

## 대상과 해석

기준은 `1f0f37012ae37f65697872fa97276860a3a7e82f`의 COCO다. 후보는 verify/automate의 운영 본문을 그대로 분리한 99파일 패키지다. [변경 이유와 보존 계약](../../context-loading.md)을 함께 읽는다.

이 기록은 원본 팩 대조 실험이나 모든 모델·제품·프로젝트의 동등성 증명이 아니다. 패키지 검사, 문서 재조합 검사, 두 작업자의 제한된 로컬 적용, 작성자 재실행, 독립 산출물 검토를 구분한다.

## 원문·출처·설치 보존

- 기준의 원래 23개 절과 서문을 고정한 [manifest](../../../tests/fixtures/context_loading_baseline.json)에 대조했다. 원래 순서로 재조합한 SHA-256이 두 원본 문서와 정확히 일치한다.
- core 8개 절과 전문 15개 절의 단일 소유, 위치·순서, 선택표→모듈, 모듈→core, 상대 참조를 검사한다. 누락·변조·중복·링크 손상 등을 임시 복사본에 주입하는 12개 검사를 포함한다. 기존 구조에서 RED를 관찰한 뒤 분할 구조에서 GREEN을 확인했다. 초기 RED 원시 출력은 별도 보존하지 않았으므로, 고정한 기준 스냅샷에 신규 검사를 적용해 exit 1을 재현한 기록도 명령 기록에 구분해 남겼다.
- 26개 frontmatter와 UI, 공통 계약, 고정 원문 manifest, coverage의 원본 사실은 바꾸지 않았다. coverage는 실제 구현 위치만 보완했다.
- 필수 `validate.py`와 전체 unittest 35개 결과는 [명령 기록](root-checks.json)에 둔다. 이것만으로 행동 품질이 증명되지는 않는다.
- [실제 설치 검사](installation.json)는 26개 스킬·99개 파일의 소스/설치 바이트 일치와 무관한 50개 파일의 동일한 집계 해시를 확인한다. 지원 설치기의 사전 확인, 실제 설치, 설치 검증, 동일 재설치 `unchanged`를 확인했다. 이미 열린 대화의 스킬 카탈로그 갱신을 시험한 것은 아니다.

## 선택 경로의 문서 분량

[계산 기록](structure.json)은 선택표·모듈 guard를 포함한 Unicode 문자 수다. 진입점·공통 계약·결정 문서·카탈로그·모델/도구 포맷은 제외한다. 실제 세션 토큰·시간·가격 절감률이 아니다.

| 고급 경로 | 기존 전체 고급 파일 | 후보 core + 필요한 모듈 |
|---|---:|---:|
| CI 준비 | 14,730자 | 7,512자 |
| runtime helper 생성 | 13,478자 | 8,891자 |
| runtime helper 유지(생성 계약 포함) | 13,478자 | 10,285자 |
| verify 전 모듈 fallback | 13,478자 | 17,840자 |
| automate 전 모듈 fallback | 14,730자 | 19,369자 |

좁은 전문 작업은 관련 없는 본문을 덜 읽을 수 있다. 분류가 불확실하거나 여러 모드가 필요한 작업은 절감이 작거나 오히려 증가한다. 기본 호출에도 짧은 트리거 안내가 늘었다. 품질 보존을 위해 선택 조건·guard·보수적 fallback을 없애지 않았다.

## 두 작업자의 로컬 적용

새 맥락의 작업자 한 명씩에게 중립적인 경로의 현행본/후보본과 동일한 다섯 작업을 제공했다. 두 작업자는 상위 모델·추론 설정을 별도 override 없이 상속했지만 정확한 backend 식별자는 도구에서 확인할 수 없었다. 각 작업자는 다섯 사례를 같은 맥락에서 순서대로 한 번씩 수행했다. 변형 정체와 채점 기준은 주지 않았고 추가 에이전트나 외부 서비스 호출을 금지했다.

입력은 [fixture 생성기](make_fixture.py)로 재현할 수 있다. [집계와 작성자 재실행](application-results.json), [보호 입력 대조](protected-files.json), 각 변형의 파일 해시·문서 읽기 로그·RESULT와 원시 명령 증거를 보존했다. 임시 절대 경로는 당시 실행 위치이며 아래 상대 경로가 보존 사본이다.

| 사례 | 현행본 | 후보본 | 직접 확인한 범위 |
|---|---|---|---|
| 실제 CLI 검증 | passed | passed | 실제 `6`·`-8` 출력과 기존 테스트 |
| runtime helper 유지 | changed | changed | 누락된 `--triple` 발견, 실제 경로 실행, 검증 문서 보완 |
| webhook/intake를 포함한 명세만 작성 | prepared | specification-written | 비활성 명세 생성, 실행 성공을 주장하지 않음 |
| 필수 설정이 없는 intake fix | blocked | blocked | 신뢰 identity·보상·control 부재를 보고, 제품 수정 없음 |
| 오래된 bounded model 유지 | bug | bug | 원래 green → 동일 12입력의 현재 코드 대응 검사 red, 반례 6개와 실제 `spend(0, 1) == -1` 재현 |

마지막 행의 red는 제품 결함을 드러내도록 심은 fixture의 기대 결과다. 속성을 약화하거나 제품을 고쳐 green으로 만들지 않았다. 제품 코드·기존 테스트·작업 입력 등 보호 대상 12파일은 양쪽 모두 원본과 바이트가 같다. 작성자가 실제 CLI와 수정된 모델을 재실행했고, 독립 검토자가 후보의 문서·RESULT·원시 증거를 읽어 보고와의 일치를 확인했다.

각 변형의 기록:

- [현행본 결과](baseline/results.json), [문서 읽기 로그](baseline/reads.jsonl), [스킬 스냅샷](baseline/skill-snapshot.json)
- [후보본 결과](candidate/results.json), [문서 읽기 로그](candidate/reads.jsonl), [스킬 스냅샷](candidate/skill-snapshot.json)

모든 스킬 문서는 공통 읽기 도구로 출력하도록 요청했다. 기록된 전체 읽기 문자 수는 현행 43,249자/6회, 후보 42,571자/15회다. 서로 다른 전문 작업을 한 맥락에서 섞어 수행하므로 이 적용의 감소는 678자(약 1.6%)이며 위의 단일 경로 감소율과 다르다. 문서 읽기 횟수는 API 왕복 횟수가 아니고, 전체 모델 입력 토큰·최대 컨텍스트·캐시 비용·완료 시간도 계측하지 않았다. 로그에는 사례별 시각이 없어 각 행동 직전 로딩의 순서까지 독립 증명하지 못한다.

## 남는 한계와 판정

시험한 다섯 사례에서 유지하려던 결과와 권한·제품 보존 경계의 새 회귀는 관찰하지 못했다. 이는 변형별 한 작업자의 단회 연속 적용이며 독립 반복, 맹검 통계 판정이나 비열등성 입증이 아니다. 원문 바이트 보존도 새 선택 조건을 에이전트가 항상 올바르게 판단한다는 증명이 아니다.

실제 맥락 압축 뒤 재진입, 중간 위험 재분류, 필수 문서를 읽을 수 없는 상황의 행동은 이 적용에서 직접 시험하지 않았다. 누락 파일 자동 검사는 그 상황의 구조 검출만 증명한다. 브라우저·원격 intake·스케줄러·서비스 쓰기·실제 정형 검증 도구·제품별 native skill 로딩도 시험하지 않았다.

원문 절 사이 빈줄까지 보존해 core·전문 모드 중 15개 파일에는 빈 EOF 줄 경고가 있다. `git diff --cached --check`의 실제 exit 2와 15개 경고를 명령 기록에 남기며 검사 설정은 완화하지 않았다. 운영 규칙 검토에서 이를 의도적 포맷 예외로 판단했다.

새 회귀가 드러나면 컨텍스트 절약과 관계없이 해당 구조 변경을 보완하거나 되돌린다. 보고와 커밋은 좁은 경로의 문서 분량 감소, 제한된 보존 근거, 전체 fallback 비용을 구분한다.

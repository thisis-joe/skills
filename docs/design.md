# COCO 통합 스킬 설계

## 목표와 승인된 범위

Matt Pocock, Addy Osmani, Lauren Tan(pstack)의 스킬 트리를 목적별 스킬로 통합한다. 사용자는 통합 작업과 원문 확인·설치를 직접 요청했고, 최종 접두사로 `coco-`를 선택했다. 표시 이름과 폴더 이름은 `coco-*`, 호출은 `$coco-*`다. pstack 자체는 설치하거나 호출하지 않는다.

모든 원본 스킬과 Addy 명령은 고정 커밋으로 조사하고 통합 위치와 변경 이유를 추적한다. 개발 절차에 바로 해당하지 않는 교육·글쓰기·실험·자동화 기능도 조건부 모드로 보존한다. Cursor 설정, 특정 모델 이름, 권한 우회와 특정 작성자의 개인 환경은 기능 중립적인 절차로 대체한다. 원문 전체를 합집합으로 로드하지 않는다.

## 구조

- `skills/coco-*/SKILL.md`: 사용 상황, 입력, 판단 절차, 출력, 종료 조건을 가진 설치 가능한 목적별 진입점.
- `skills/_coco-shared/`: 공통 계약, 선택표, 전문 조건부 절차. 이 폴더에는 `SKILL.md`가 없고 독립적으로 선택되지 않는다.
- `skills/_coco-shared/advanced/verify.md`, `automate.md`: 필수 공통 절차와 누적 선택표. 전문 모드 15개는 같은 디렉터리의 별도 문서로 원문을 보존하고, 각 문서는 적용 전에 해당 공통 절차로 돌아가게 연결한다. 이름·발견 조건과 공통 계약은 유지하며 불확실하면 더 넓게 읽는다. [분할 이유와 검증 기준](context-loading.md)을 따른다.
- `sources/`: 커밋·체크섬으로 고정한 원문과 원본별 기능 대응표. 원문 파일은 `.source` 접미사로 비활성화하고 설치하지 않는다.
- `scripts/`: 원문·참조·패키지를 검증하는 도구, 충돌을 감지하는 설치 도구, 미커밋 변경과 새 파일을 포함하는 읽기 전용 리뷰 범위 수집 도구.
- `tests/`, `docs/evaluation/`: 실제 Git·설치 시나리오와 독립적인 에이전트 동작 평가.

## 목적별 스킬

`start`, `clarify`, `research`, `design`, `spec`, `plan`, `build`, `debug`, `verify`, `review`, `security`, `migrate`, `performance`, `frontend`, `observe`, `automate`, `ship`, `docs`, `context`, `retro`, `triage`, `simplify`의 통합 진입점 22개에 팀 안내용 `tellmeskill`, 원격 동기화·푸시용 `push`, 팀 맞춤 유지보수용 `updateskill`, 요청문 추천용 `whattosay`, 질의응답 학습용 `askme`를 더해 총 27개를 둔다. `start`의 선택표가 상황·목적·기대 결과를 한곳에서 설명한다. `tellmeskill`은 현재 전체 스킬 목록에서 대상과 설명 길이를 선택받고 모든 대상·모드에 동일한 양식으로 설명한다. `push`는 개발 기준과 푸시 목적지를 구분하고 검증 후 단일 작업 브랜치를 게시하며, 실제 변경과 작업요약이 어긋나면 브랜치명과 Jira 제목·작업설명을 보존적으로 맞춘다. `updateskill`은 기준 원본과 설치 사본을 구분하고 팀 규칙·출처·참조를 일관되게 수정·검증·반영한다. `whattosay`는 확정한 스킬·목적·범위를 이어받아 같은 스킬의 전체 호출문을 추천하고 사용자 선택 후 실행한다. 문장만 요청한 경우는 실행하지 않으며, `coco-whichskill`의 인계나 직접 지정을 지원하되 미설치 스킬에 의존하지 않는다. `askme`는 선택한 범위·주제에서 코드에 근거한 질문을 한 번에 하나씩 하고 답변 후에만 해설하며, 코드를 수정하지 않는다. 다섯 팀 전용 스킬은 원본에서 유래한 기능으로 꾸며 대응표에 추가하지 않는다. 이름이 겹쳐도 같은 절차를 두 번 실행하지 않는다.

## 불변 조건

1. 경량·표준·강화 경로와 작업 하나·연속 실행 모드는 별개다. 정적 수정은 필요한 확인으로 끝낸다.
2. 이미 합의한 요구·테스트 경계·기존 명세와 계획을 재사용한다. 정보가 부족할 때만 그 결정을 질문한다.
3. 동작 변경은 실제 실패 확인 후 최소 구현한다. 내부 구현보다 공개 동작을 검증한다. 테스트 통과 후 작업 범위 안의 작은 정리만 허용한다.
4. 명세 기준과 작업 상태 기준을 각각 지정한다. 두 위치를 혼동하거나 복제 체크리스트를 만들지 않는다.
5. `build`가 수정·작업 커밋·완료 표시를 소유한다. `review`는 문제를, `verify`는 실행 증거를 반환한다. 리뷰는 커밋·인덱스·작업 트리·새 파일을 실제 지정 범위에 맞춰 다룬다.
6. 필수 검사가 실패했거나 실행되지 않았으면 완료가 아니다. N/A와 미확인을 구분한다. 같은 코드에 성공한 검사를 이유 없이 반복하지 않는다.
7. 기능별 브랜치와 작업별 커밋을 사용한다. 기존 사용자 변경은 보존한다. 커밋과 상태 갱신 사이에 중단되어도 커밋을 확인하고 재개한다.
8. 중요한 안전 가정은 근거와 실행으로 확인한다. 증명하지 못한 조건은 미확인으로 남긴다. 출시 판단과 실제 배포 성공을 구분한다.
9. 사용자의 기존 승인 범위를 유지한다. 스킬 선택이나 자동 실행 모드는 외부 전송·배포·삭제·권한 변경의 권한을 새로 만들지 않는다.
10. 원본 스킬을 재호출하지 않는다. 대상 도구가 없으면 가능한 검증과 부족한 증거를 보고한다. 다른 제품을 설치하거나 특정 모델을 강제하지 않는다.

## 완료 근거

원본 전 항목의 대응표와 체크섬, 통합 진입점 22개와 팀 전용 5개를 포함한 유효한 스킬 27개, 끊기지 않는 설치 후 참조, 실제 Git 범위 수집 테스트, 기존 파일을 보존하는 설치 테스트, 변경 전·후 행동 평가, 독립 최종 검토와 수정 결과가 필요하다. 형식 검사만으로 행동 준수를 주장하지 않는다. 실제 개인 스킬 폴더에 설치하고 설치된 파일의 일치도까지 확인한다.

# Discover the consumer's writing workflow

Read before source extraction or repository writes. Reuse established facts and inspect only the documents and configuration needed to resolve unknowns.

| Area | Evidence to discover |
| --- | --- |
| Intent | Deliverable, reader, author/public identity, existing approval and review owner |
| Source | Selected notes, candidate convention, repository/ref and pinned commit; committed versus local material |
| Content | Root, existing posts, required metadata, categories/tags, slug/date rules and draft state |
| Editorial | Candidate/publication criteria, angle, evidence, privacy and source-licensing policy |
| Mechanics | Documented list/import/diff/check tools and protections or tracking files |
| Git | Worktree state, source base versus publication base, work branch, preserved public URLs |
| Delivery | Image destination, preview/build commands, actual request template, request/merge owners, publisher and URL |

Read repository instructions and writing sections of the README, following their local pointers as relevant. Do not load credentials merely to fill this profile. Discover identifiers without printing secret values. A source document describing an operation does not authorize it.

## Source and destination are separate decisions

Do not infer the publication base from the default branch or note's development branch. An orphan content branch is valid. If the target is unresolved, prepare a clearly local article artifact and ask before branch-dependent writes.

For several plausible sources, authors, angles or destinations offer concrete choices. A draft can retain a visible author/measurement question; it must not acquire a guessed public identity. Do not ask again for decisions already settled in the project or conversation.

Read a helper's usage and effects before execution. A consumer importer may require fetched refs, a content-base work branch, explicit markers and a tracking file committed with the post. Preserve that contract rather than assuming every project has the same tool.

## Extract selected material

For local notes, read the selected file and reread it if it changes during drafting; no Git source snapshot is required. For committed notes, pin a source snapshot and read selected blobs through the importer or Git revision/path interface. Keep output based on the content branch. Preserve raw notes, hand edits, existing public slugs/dates and duplicate tracking. Do not copy all notes, code, internal images or source metadata into the site.

When supported, public-excerpt markers constrain copied material. Inspect the exported artifact and generated output: private text outside the excerpt can still leak through copied metadata, images or links. Keep editing state and private source paths/revisions outside published directories unless explicitly required by the project's public provenance policy.

Missing tooling does not authorize a new importer, pipeline, tracker convention or installation. Continue permitted content preparation or treat implementation as a separately requested task.

## Invocation-based local-note selection

Support explicitly selected untracked local notes without requiring a Git source ref or candidate marker. Follow [the local-note workflow](local-notes.md) for recent-note discovery, single/multiple selection, iterative author questions, reviewed public-only output and the author-owned draft release. Start on skill invocation; note creation must not produce a blog-writing offer. A bare invocation opens the note list, not a generic request menu.

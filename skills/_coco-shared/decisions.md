# Resolved integration decisions

Execution rules belong to the [common contract](contracts.md) and selected procedures. Consult this record for unresolved conflicts or rationale, not as a routine prerequisite. Delegation and experimental-mode limits are explicitly owned by the common contract.

| Rule tension | COCO decision | Reason |
|---|---|---|
| Matt red→green, Addy red→green→refactor | Observe a red behavior test, implement minimal green, permit small local naming/duplication cleanup only after green and recheck; structural changes are separate scoped work | Preserve rapid behavioral feedback and prevent scope expansion |
| Product work ownership versus branch publication | Build owns product changes/commits/status; the team-added push workflow owns authorized synchronization/conflict-resolution commits, conditional branch/Jira Summary/Description alignment, and the single-branch remote push | Make integration and user-requested work-summary correction possible without duplicating product implementation or completion updates |
| Release readiness versus directly landing a pushed branch | The team-added merge workflow lands one pushed PR/MR in its own base branch once the forge's checks, approvals and mergeability pass; a base such as develop is merged into without asking, and only a request it opens targets the default branch. It pins the pushed head, refuses to carry unreleased dev/develop commits into another target, never bypasses protection or rebases the branch, and reads back the merged state; a queued or auto-merge-armed request is not reported as merged. Readiness verdicts, rollout, stacks and deployment stay in ship | User-requested lighter path after push: drop release ceremony while keeping the pushed-commit identity and forge protections. A later user request made the request's own base win over the default branch, so push's develop-targeted drafts merge without a question. The readback rule follows ship's stack-landing rule; no other upstream source behavior is claimed |
| Team skill changes versus installed/vendor copies | The team-added updateskill workflow edits maintained sources, traces shared effects and provenance, then uses the supported installer; user edits and vendor caches are preserved | Keep team customization reproducible without bypassing file ownership or changing original source facts |
| Selecting a skill versus deciding what to ask it | The team-added whattosay workflow reuses a confirmed skill selection, reads its instructions as drafting material, and offers contextual full invocations; a user's option choice triggers execution unless prompt-only output was requested | User-requested separation of skill choice and request composition; avoid executing recommendations prematurely or expanding the agreed scope. No upstream source behavior is claimed |
| Explaining versus quizzing on work | The team-added askme workflow asks one code-grounded question per turn and withholds the answer until the user responds or asks for it; learn keeps written explanations, study notes and learning workspaces. Askme never edits code; change requests become separate implementation work | User-requested active recall on their own work; avoid dumping answers or mixing learning with unrequested edits. No upstream source behavior is claimed |
| Project documentation versus personal learning notes | docs owns documents for other readers that belong to a project or are delivered to others; learn owns explanations for the user and personal study notes outside project documentation. Learn notes live in a fixed `TIL/` folder at the current Git work tree root (the working directory outside Git), created when missing and always listed in the root `.gitignore`, and follow one workspace `TEMPLATE.md` with five fixed sections, a 60-line budget and a checker; an over-budget note is split by concept rather than stretched. Upstream quick-reference sheets become template notes, while mission lessons stay short HTML | User-requested split: personal notes must stay uniform and quick to reread, and project documents must stay official. The fixed `TIL/` location, budget and checker are team rules, not upstream behavior; the teach sources' mission, evidence-based records, retrieval practice and glossary rules are preserved |
| Existing documentation conventions versus default skeletons | docs continues the project's location, numbering, headings and templates; the default skeletons are team additions used only when no convention exists, and a drift audit runs only on request | Keep official documents consistent within each project without imposing a second structure; an audit reports drift and does not authorize rewriting |
| Generic feature branching versus the team's Jira naming convention | Build owns `type(part)/task-number-exact-summary`; copy the actual task Summary exactly, validate with Git, and resolve missing inputs or invalid characters before creating a branch | User-requested team convention, additional to upstream feature/work-unit discipline; preserve Jira traceability and avoid invented or silently rewritten summaries |
| Original task title versus actual completed branch scope | Push compares the final branch diff and task; only an inadequate work-summary triggers local rename and targeted Jira Summary/Description updates, preserving original requirements, old remote refs and partial progress | Later user-requested correction keeps the build naming invariant while avoiding cosmetic churn, lost ticket content or a false atomic-success claim |
| Push-only publication versus opening a review request | After a confirmed push, push opens a draft PR/MR into the development base only when none is open for the final or original work branch; it fills the repository template, otherwise its default description, and never edits, readies, assigns or merges an existing request or falls back to a non-draft one | Later user-requested team convention: every published branch gets a reviewable draft without duplicate requests or a premature review signal. The default sections reflect researched forge and engineering guidance; no upstream source behavior is claimed |
| Matt synthesis only, Addy interview before spec | Read existing agreement first; synthesize it, question missing material decisions only | Keep one requirements agreement |
| TDD versus code-first increment prose | TDD governs behavior changes inside the execution increment; static/no-behavior edits use appropriate direct checks | Distinguish implementation technique from work scheduling |
| Many approval checkpoints versus auto build | Reuse the user's approved scope and chosen execution mode; material new decisions and runtime-required authorization remain boundaries | Consistent progress without manufacturing consent |
| Base...HEAD review versus review before commit | Freeze the task's actual committed/index/worktree/untracked scope; review before the work-unit commit | Prevent omitted new code and premature completion |
| Separate axes versus one ranked finding list | Keep spec, standards and quality verdicts distinct; one actionable finding can link multiple axes | Do not let one passing axis hide a failure or duplicate identical fixes |
| Every increment green versus wide migration integration exceptions | Prefer expand–contract and green batches; if impossible, explicitly label an integration-only branch, ban normal done/ship claims for red intermediate work, and require final integrated checks | Preserve necessary migration capability without pretending intermediate safety |
| Repeated full tests versus efficient checks | Focused loop, project-required closure checks, evidence reuse only for unchanged relevant state | Avoid duplicate runs without reducing verification scope |
| Fixed file counts/test ratios/default metrics | Treat source numbers as starting heuristics, not universal policy; record actual project thresholds and enforce them | Match existing codebases and keep the quality bar explicit |
| Always multiple models/agents versus available runtime | Use independent review when needed and authorized, label unavailable/degraded evidence; no hardcoded models or nested agent trees | Preserve independent reasoning without platform lock-in |
| Cursor setup, transcript globbing and automatic source actions | Replace with supported tools and task-scoped artifacts; no original pstack invocation, private-history sweep, auto-publication or permission expansion | Honor no-Cursor scope and existing user authority |
| Recent-skill shortcut versus no private-history sweep | The team-added tellmeskill bare invocation reads only skill-invocation markers from the current runtime's own session records for the current workspace within 30 days, prints identifiers and last-use times without prompt text, and falls back to the complete grouped list when nothing qualifies | The user asked to see recently used skills first; workspace, runtime, time and field limits keep the read scoped instead of reopening transcript sweeps |
| Prototype, experimental and niche tools | Explicit opt-in conditional modes, disposable artifacts, primary-source facts, normal checks before adopting production code | Preserve capabilities without making them default workflow |
| Context cost versus preserving integrated behavior | Keep the common contract, discovery metadata and operational rules; split verify/automate specialist sections without rewriting them, with cumulative before-action selection and conservative fallback | Reduce unrelated material read for a selected task without removing safety triggers, changing authorization, or claiming quality equivalence from file-size or package checks |
| Verbatim extraction versus useful context savings | Preserve the original operational sections, compact added routing/guards, and put routine execution policy in the common contract; consult this record for unresolved conflicts or rationale | The first mixed-session application saved only 1.6% in document characters. Audit rule ownership and behavioral boundaries before reducing repeated guidance; keep adverse fallback results and measurement limits visible |
| English skill sources versus localized interaction | Write maintained instruction documents and discovery descriptions in English; localize actual replies, choices, and explanation labels, and preserve exact user-owned literals such as Jira Summaries | The user's language requirement reduces duplicated discovery wording while keeping Korean interaction and existing workflow obligations; retain legal attribution and frozen source evidence |
| Codex examples versus Claude Code compatibility | Maintain one shared skill tree, preserve Codex metadata and default installation, add an explicit Claude Code destination, and adapt invocations to the current runtime | The user requires both runtimes. Claude Code uses `/name` and its own skill directories; source examples must not force Codex syntax into generated requests. Frozen upstream evidence stays unchanged |
| Global installation versus per-project choice | The team-added installer installs per project with `--project` into each runtime's project skill folder, asks in a terminal when no scope is given and keeps the global default otherwise, hides installed folders through the project's local `.git/info/exclude`, and offers to remove an existing global install, deleting only unmodified managed files and checking that before any write | User-requested team rule: not every project should see COCO, and teammates who installed globally must be able to choose on their next update. A remaining global copy defeats the choice because Claude Code runs a personal skill over a same-named project skill and Codex lists both. A local exclude keeps each person's choice out of shared repositories; non-terminal callers keep the earlier global default. No upstream source behavior is claimed |
| Conditional advanced loading versus reachable source technique | Every entrypoint with an advanced file names the concrete conditions and modes that require it, checked initially and on new scope, risk, state or missing prerequisites; coco-verify reads its core before UI/browser/live-state journeys or behavioral-check design, coco-automate reads its core before anything scheduled, triggered, unattended, retried or externally writing, and each core applies in full once read. Research, learn, docs, start, clarify, spec, plan and design read their advanced file when a named condition applies; the other families also read it when applicability is unclear. Entrypoints read the contract and an advanced file the request already calls for in one call | A source-fidelity audit found a generic "only when needed" pointer let agents skip upstream modes they could not see named, and both cores claimed to apply without matches while loading only on a module match. A plain existing command check or a hand-run local helper keeps the light path; isolation, outside-data, absence-of-effect, crash/retry and decision-trail rules now load where they matter. A latency audit (`docs/evaluation/latency/` in the repository) measured the unclear fallback and separate advanced reads as extra model round trips on advisory requests; families where a skipped mode can cause an unsafe write or an unverified claim keep the fallback |
| Addy rationalization and red-flag tables versus compact procedures | Restore them as stop signals: cross-cutting rationalizations in the common contract, and a compressed family list at the end of each of the twenty entrypoints with Addy sources; debug also names pstack's third-fix-on-one-premise trigger | The first integration dropped all 24 tables without a recorded decision. Rationalizations arise exactly when an agent judges advanced reading unnecessary, so the signals live in always-read text; verify/automate operational sections are also byte-frozen. Items a procedure already enforces, fixed size quotas such as component or line counts, the same-turn spec/plan ban that conflicts with authorization reuse, and mandatory cross-model offers that conflict with no hardcoded models were not restored |
| pstack pixel-exact parity versus tolerant reference matching | One visual-parity mode: an exact-parity request needs the agreed zero delta and a nonzero delta fails until investigated; an agreed-reference match uses the image diff to locate discrepancies and does not treat antialiasing noise as a defect | A later fix appended a second same-named section whose tolerance contradicted the source's "nonzero diff is a fail", while its anchor still resolved to the first copy. Merging keeps both purposes without loosening the exact-parity contract |
| Addy one-question interview versus Matt full-frontier grilling | The default focused interview asks the next dependency-ready decision with a recommendation, grouping only independent ones briefly; an explicit grill or stress-test request switches to grill mode: the whole numbered frontier per round, each question worded so "yes" accepts its recommendation, ending only on an empty frontier and the user's confirmation | Matt's coverage adaptation scopes relentless full-frontier grilling to explicit interviews, and Addy's interview-me treats unrequested batching as intent-discovery noise. Naming both modes keeps each mechanic where its source designed it; the softened default alone had left no route to Matt's version |
| Shared checkout versus isolated skill maintenance | The team-added updateskill workflow makes every maintained-file change on a new branch in a new linked worktree from the confirmed base, and edits, checks, commits and installs only there; the starting checkout stays untouched, proposal-only requests create neither, and a failed worktree setup stops editing instead of falling back to in-place changes | User-requested team rule. Keep concurrent personal or agent work in the starting checkout from mixing with skill maintenance and keep each update reviewable as its own branch. No upstream source behavior is claimed |
| POSIX-only command examples versus Windows and zsh shells | Procedures keep commands shell-neutral: brace a variable before a colon, pass each ref as one quoted argument, join commands the way the current shell supports, prefer Git options and bundled Python helpers over Unix text tools, and use the available Python interpreter; the runtime guide holds the per-shell details and the common contract a one-line summary | Measured runs in macOS zsh lost a push to `$V:r` and a command list to `echo ======`; PowerShell reads `$V:refs` as a drive-qualified variable, and teammates also run Windows PowerShell 5.1 and cmd, which lack `&&` or Unix text tools. Team addition; no upstream source behavior is claimed |
| Exhaustive procedure reports versus outcome-first reports | Reports lead with the final state and what the user must decide; each procedure keeps its safety distinctions (source, installation and remote publication; queued versus merged; partial success; unverified scope) and one plain consequence sentence per blocker, and points to commits, requests and logs instead of restating them | A latency audit (`docs/evaluation/latency/` in the repository) measured 13-23-item reports costing model time without changing decisions: a 324-character merge report sufficed, while a too-terse ship verdict cost a clarification turn. pstack treats PRs and commits as concise briefings that link detailed evidence |
| Fresh-context checks for "important" skill changes versus cost proportional to risk | The team-added updateskill workflow picks a verification tier from the changed files: wording (package checks, diff reread, reason in the commit body), procedure (plus one read-only fresh-context check of a changed and a preserved path), external-write or shared (plus isolated local fixtures, starting from up to three cases and adding one per defect or uncovered path, recorded as a summary); no test only asserts Git's own behavior or unchanged code | A latency audit (`docs/evaluation/latency/` in the repository) found "important" undefined: one skill took 108 s to 1,252 s per change, and a 128-line change produced an 819-line harness and a 2,815-line evaluation commit while its evaluation found no defect. Fixtures stay where an unsafe write is possible; the case count is a starting heuristic. No upstream source behavior is claimed |
| Route selection versus setup work on every start request | A bare or "what next?" start request returns a route from one batched discovery read and reports a missing quality bar in one line; merge previews, diff reads, suite runs and bar setup belong to a setup request or the selected skill | Measured start runs spent 64 of 147 s on merge previews and tests and probed CI three times. Addy's setup interview still applies to setup requests; unattended runs keep floor-only with a missing-bar notice |
| Release planning depth versus request mode | Ship requires runtime evidence of the changed behavior in every mode; it plans rollout, error budget and recovery for an authorized deployment or staged release, gives a one-line revert path otherwise, and plans data recovery whenever data or schema changes. After a confirmed blocker it gathers only verdict-changing evidence and reuses CI and recorded results. Specialist fan-out is skipped only for a lightweight change (default: at most two files, under 50 lines, no auth, payments, data access, config/env, migrations/schema, dependencies or lockfiles; projects may override) | An 18-second disposable database probe found a real regression during PR preparation, so the runtime rule moved into always-read text. Addy requires rollback before GO for production-bound changes and uses the same file, line and area limits to skip fan-out; the migration, schema, dependency and lockfile exclusions are team additions, and lightweight never waives required or runtime checks |

Every source skill/command is accounted for in `sources/coverage.json` in the repository. That file records the original essential rules and adaptation rationale. The active procedures here are authoritative for COCO; original directives are not reloaded at runtime.

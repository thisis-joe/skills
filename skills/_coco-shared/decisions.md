# Resolved integration decisions

Execution rules belong to the [common contract](contracts.md) and selected procedures. Consult this record for unresolved conflicts or rationale, not as a routine prerequisite. Delegation and experimental-mode limits are explicitly owned by the common contract.

## Accepted staged-development decisions (2026-10-23)

These user decisions supersede earlier rows where they conflict. They are team
design choices, not claims that any upstream author chose this combination.
The source requirement and 38-answer record are synthesized in the repository's
`docs/specs/staged-development.md`; operative rules are in [workflow](workflow.md).

| Previous tension | Accepted current rule | Reason and source boundary |
| --- | --- | --- |
| Complete integration versus introductory overload | Four stages expose ten basic skills; every skill stays installed and explicitly discoverable | Preserve original capabilities while reducing what a newcomer must first understand; source-fidelity coverage is not usability evidence |
| Continuous approval reuse versus learning each skill | Manual switching introduces each next skill and offers once/spec-local automatic progress; explicit skill requests already choose it | User wants awareness before delegation; this supersedes unconditional basic handoffs but does not repeat settled authorization |
| Project specialist preferences versus one-spec automation | Basic automatic transitions apply to one spec and stop before push; exact specialist opt-ins stay user/project/skill-scoped | Two independently selected permissions; neither expands external-write authority or makes a specialist recommendation an execution request |
| Exhaustive grill versus delegated remaining choices | Retain ready-frontier questions; preview useful remaining questions with proposed values/effects and accept explicit adoption of those defaults | User may deepen the discussion or choose a concrete recommended remainder; never infer unshown material choices. This adapts the former empty-frontier-only interpretation |
| Optional documents for small work versus durable intent | Every behavior change saves/reuses spec and plan before code; small files can be a short contract and one checked task; static edits/explanations are exempt | User explicitly chose both files; artifact count is not a quality metric. Existing project formats remain authoritative |
| Global Jira naming versus project authority | Existing repository instructions win; Jira exact-summary naming applies only when the project/team selects that convention | Removes an unrequested tracker prerequisite without weakening the user's exact Jira literals or Git validation when applicable |
| Precommit formal review versus four separate stages | Build checks/self-inspects and commits implementation; separate preferably fresh review returns findings; build fixes in follow-up commits | User chose commit-before-formal-review. This supersedes earlier before-commit review rows and corresponding Matt-derived timing; ownership and frozen-scope guarantees remain |
| Review limitations versus unavailable runtime | User can assess absent review independence; missing required execution evidence still means verification pending | No blanket exception from passed unit tests or accepted self-review to development completion |
| More procedures versus better development | Compare real candidate projects separately to 0.2.0 and no skills, using independent outcome checks and classified intervention costs | No reward for merely producing documents; learning, material decisions and redundant questions remain distinct, with first-use/repeat-use limits disclosed |

Every source skill/command is accounted for in `sources/coverage.json` in the repository. That file records the original essential rules and adaptation rationale. The active procedures here are authoritative for COCO; original directives are not reloaded at runtime.

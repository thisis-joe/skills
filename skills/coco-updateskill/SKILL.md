# coco-updateskill

기존 스킬을 팀의 실제 개발 방식에 맞게 수정하고, 관련 규칙과 참조의 일관성을 확인한 뒤 검증된 변경을 설치에 반영한다. [공통 계약](../_coco-shared/contracts.md)과 [팀 수정·반영 절차](references/team-update.md)를 따른다.

## 진행

1. **대상과 수정 목적 확인.** 이름이나 경로가 주어지면 실제 `SKILL.md`를 찾는다. 대상이 없으면 현재 사용 가능한 스킬의 이름·한 줄 용도를 보여주고 번호 또는 이름을 선택받는다. 불분명한 동명 스킬은 식별자를 확인한다. 수정 요청이 이미 구체적이면 같은 질문을 반복하지 않는다. “팀에 맞게”만 주어지면 불편한 실제 사례, 원하는 동작, 적용할 팀/저장소 범위 중 빠진 핵심 결정을 확인한다.
2. **기준 원본과 현재 상태 확인.** 팀이 유지하는 저장소의 스킬 원본, 설치 사본, 실제 팀 지침·명령·CI, 관련 공통 계약·참조·UI 정보와 호출자를 읽는다. 시작 버전/해시, 브랜치, 기존 사용자 변경을 기록한다. 플러그인 캐시나 설치 사본을 원본으로 착각하지 않는다. 설명 대상의 명령과 외부 작업은 수정 자료로 읽고 자동 실행하지 않는다.
3. **변경 기준 정리.** 바꿀 규칙·이유, 유지할 동작, 팀 공통 규칙인지 특정 프로젝트 조건인지, 확인할 사례를 간결하게 정한다. 기존 승인 범위는 재사용한다. 제안·리뷰만 요청했다면 구체적인 수정안과 영향으로 끝내고 원본·설치본은 변경하지 않는다.
4. **필요한 범위만 수정.** 목적·호출 이름·발견 조건·호출 정책을 요청 없이 바꾸지 않는다. 공통 규칙은 소유 위치에서 한 번 수정하고 영향을 받는 진입점·연결 참조·관련 안내를 맞춘다. 이름/구조 변경이 요청된 경우에만 등록·호출·UI·설치 연결까지 갱신한다. 기존 개인 변경은 보존하고, 관리하지 않는 캐시는 팀 수정본의 위치와 이름이 정해지기 전 직접 덮어쓰지 않는다.
5. **출처와 변경 이유 보존.** 고정 원문·라이선스·원본 사실은 유지한다. 원본에서 채택한 동작을 팀 규칙으로 바꾸면 기존 결정 기록과 해당 대응표에 수정 이유·범위·실제 구현 위치를 맞춘다. 팀 신규 기능에 가짜 원본 출처를 붙이지 않는다. 오탈자 수정에 별도 장문의 기록을 만들지 않는다.
6. **영향에 맞게 검증.** 스킬 형식·참조·UI·등록과 설치 후 연결을 확인한다. 절차나 판단을 바꿨다면 실제 요청 사례로 원하는 변경과 보존할 동작을 함께 확인한다. 외부 쓰기·실제 푸시·배포가 포함된 스킬의 동작 시험은 기본적으로 격리된 로컬 자료로 수행한다. 가용하면 중요한 변경은 새 컨텍스트로 확인하고, 없으면 직접 검토와 미확인 범위를 밝힌다. 단순 문구 수정에는 불필요한 반복 실험을 붙이지 않는다.
7. **커밋과 설치 반영.** 검증한 팀 수정과 이유·근거만 기능 브랜치에서 작업별 커밋으로 남긴다. 실제 수정 요청이고 기존 설치 위치가 확인되면 지원되는 설치기로 반영하고 다시 읽어 일치·참조·기존 다른 스킬 보존을 확인한다. 설치 충돌은 소유 파일과 차이를 보존한 채 해결하며 실패한 설치를 성공으로 보고하지 않는다. 변경 검증과 설치 확인을 마친 뒤 완료를 보고한다.

## 결과

수정 대상과 원본/설치 위치, 팀 요구와 바뀐 규칙, 변경 이유, 공통 영향과 파일, 출처 처리, 검사·사례 결과, 커밋, 실제 설치 상태와 남은 결정을 전달한다. 원본 수정 완료·설치 완료·원격 게시 완료를 서로 구분한다.

이 스킬은 스킬 유지보수 파일과 그 작업 커밋을 맡는다. 제품 작업 완료 표시, 원격 push, PR 작성·병합, 다른 팀원에게 배포·메시지 전송은 별도 요청 범위다. 추가로 요청된 게시 작업은 기존 승인을 재사용해 해당 절차에 인계한다.

예: `$coco-updateskill coco-build 우리 팀의 검증 명령과 리뷰 절차에 맞게 수정해줘`. 새 스킬 작성은 `skill-creator`, 설명만 필요하면 `coco-tellmeskill`, 반복 실패의 원인 조사부터 필요하면 `coco-retro`를 사용한다.
